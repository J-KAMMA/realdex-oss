# RealDEX v0.18 — Aptos実ノード統合・決済応答検査

作成日: 2026-09-06（日本時間）。未監査のローカル開発版。本番資産・本番鍵の使用禁止。

## 基準と版の整合

今回の基準は `RealDEX-Cosmos-Settlement-v0.17-2026-09-06.zip`、SHA-256 `4e197659203a0a2a2c1edea15e3fd7f0ecc0a3b36acb3538b896b753530eef09` です。入力ZIPの1,259ファイルを同梱ハッシュ一覧と照合して一致しました。

同じ会話の2026-09-06版v0.16には別構造のAptos実ノード試験がありましたが、このv0.17には含まれていませんでした。過去の文章から合格を継承せず、固定ツールの識別情報を照合し、現在のAccountEngine・所有者HTTP APIに試験を移植・拡張しました。古い枝のアカウント実装全体を上書きする変更はしていません。

## 実ノードで再現した不具合

実Aptosノードの送金準備が `APTOS_TRANSACTION_MISMATCH` で停止することを、修正前に再現しました。原因は、実際のシミュレーション応答にない `type` を必須にしていたことです。シミュレーションにだけ省略を認め、収録取引のtype必須は維持しました。

また、RPCが先頭ゼロを省く同じアドレスを返す場合に備え、ノード応答のfrom/to/認証鍵を32バイトへ正規化しました。所有者の入力は完全な長さのままです。先頭ゼロになる送受口座を固定して実ノード試験へ入れています。

`success` と `vm_status` の矛盾、ブロックversion範囲の逆転、観測済みブロックのversion範囲・時刻の変化を拒否します。受取照合では実行前後versionの残高・sequence・費用を既存通り確認します。

## Stellarの失敗結果を厳密に読む

旧版は負の結果コードを広く受け入れ、不正な失敗XDRを `reported-reverted` にできることを回帰試験で確認しました。今回、一つの通常Paymentの結果だけを全バイト解析し、tx・operation・payment結果、fee、拡張終端、成功フラグを一致させます。未対応・不完全な失敗は未解決のままです。

元の合成fixtureにも短すぎる失敗XDRが含まれていたため、仕様に沿うtxFAILED＋一つのPayment結果へ直しました。正しい失敗を拒否するためではなく、不正な応答を成功した解析として扱わないための変更です。送信元sequenceの消費も確認します。実Stellar Core試験は行っていません。

## 共通RESTの入力境界

不正UTF-8、JSONの重複メンバー、精度を失う数値、負のゼロ、孤立サロゲート、危険なキー、深すぎる構造を拒否します。

数値変換後だけの検査では、`1.0000000000000001`が`1`へ、`1e-9999`が`0`へ丸められて通ることを配布候補で再現しました。元の数値表記とlossless parseも照合するよう修正しています。このREST境界では非引用数値を安全な整数表記だけに限定し、`1.0`や`1e0`も拒否します。これらがJSON仕様上不正という意味ではなく、クライアントの対応範囲を明示的に狭めたものです。引用された残高・version・小数文字列は丸めず維持します。正負の上限、入れ子、分割受信、固定seedの256組の整数と微小端数を含む回帰試験を追加しました。256組はテスト1件の内部ケースで、成功件数に別途加算しません。大きな金額やversionは文字列のまま処理します。パス・メソッド・queryを読み取り・シミュレーション・送信の用途ごとに限定し、未知の追加パラメーターや重複queryを拒否します。

Aptosの成功HTTP応答にはchain IDと台帳versionのヘッダーを求め、履歴指定が報告された範囲内かも検査します。ただし、ヘッダーとJSONの両方が偽造される状況を暗号学的に防ぐものではありません。独立した状態証明・最終確定証明とは区別します。

修正前の19回帰ケースは19件失敗し、修正後は19件成功しました。これは19種類の重大脆弱性が見つかったという意味ではなく、応答型・照合・境界条件を検査するケース数です。追加の互換性・XDR・query試験と、試験ツール／合否判定の試験も含めています。

## 実Aptos試験

固定Aptos CLI 9.5.1（core Git `6d836beedc56fc70c54f3b3046d1d248d850c64b`）の一つのローカルvalidatorでMoveを実行しました。二つのHTTP URLは同じvalidatorへの中継であり、独立した二つの台帳ではありません。正常処理は実ノードから取得し、通信断・応答改変は転送層で注入します。

16シナリオ: 正常送金と残高／ガス差分、先頭ゼロの送受アドレス、同じ依頼の重複防止、署名のみ保存から初回送信、応答喪失から再照合、残高不足、実VMでのガス不足、外部取引によるsequence競合、シミュレーション中のロック、保存失敗、偽の受取先、矛盾した成功状態、改変された履歴残高、checkpoint不一致、設定変更後の送信拒否、再起動後の署名とsequence予約保持です。

デモでは1,000,000 octasを送金し、受取残高は1,000,000増加、送信元は送金額＋498,300 octasの実手数料だけ減少しました。同じ依頼を繰り返しても送信は1回です。この手数料はローカル試験値で本番予測ではありません。シミュレーションの署名はすべてゼロです。

## 互換性・変更範囲

保管庫形式、暗号、鍵導出、保存・ロック本体、署名権限は変えていません。v0.17の合成署名記録をv0.18で復元し、署名・記録の一致、復元直後のロック、署名前のバックアップ要求を確認しました。これは古いバックアップや別端末をまたぐ二重署名防止ではありません。

既存 `contracts/`・`src/`・`node/`、ルートの依存指定・lockfileは維持しています。所有者画面の説明だけは、Aptosの単一実ノード検証とStellar未検証を区別する文に更新しました。AI・共有ノード・外部アプリの送信権限は増やしていません。

`selectedScopePassed` と実Aptos試験はtrueでも、`fullLocalAcceptancePassed` と `productionReady` はfalseです。
