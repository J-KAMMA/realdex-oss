# RealDEX v0.16 — 安全性の境界

## 本番判定
未監査のローカル開発版です。Stellar/Aptos新規経路の実ノード適合・VM実行・分散合意は未検証です。署名を生成できることと、安全な本番決済が確認できることは同一ではありません。実資産や本番秘密鍵を使わないでください。

## 所有者と共有ノードの分離
追加APIは既存の所有者用loopbackサーバーに限定しています。AI用MCPとdappの権限表には追加していません。AIはウォレット解除、設定追加、非EVM署名を呼び出せません。共有ノードに秘密鍵、所有者capability、承認権を渡しません。

同じPCの任意ファイル・メモリ・画面を読む権限まで持つAI/マルウェアを、プロセス分離だけで隔離できるわけではありません。OSの鍵保護、ハードウェア署名器、サンドボックスは未実装です。

## 通信・設定
明示的な127.0.0.1 HTTPの2〜4URLに限定し、任意のホストや認証URLへ自動接続しません。REST呼び出しは必要なパス/HTTPメソッドだけを許可します。リダイレクト禁止、10秒のタイムアウト、512KiBのJSON応答上限を設け、RPCの任意エラー本文を所有者ログへ転記しません。

チェックポイントと設定fingerprintは履歴に結び付きますが、その最初の正しさは利用者が独立に確認する必要があります。同一ノードの別入口や共謀する複数RPCが一致しても、真正なチェーン状態の証明ではありません。loopbackプロキシが本番へ中継しないことも利用者側の管理対象です。

StellarはStandalone passphraseを署名に含みますが、誰でも同じpassphraseの別ネットワークを作れます。Aptosはchain ID 4を署名に含みますが、それも同じIDを使うネットワーク間の世界的な一意性を証明しません。

## 承認・永続化・停止
署名直前と初回送信直前に状態・期限・sequenceを再検査します。所有者の全文受取先確認、バックアップの読み戻し確認、プロファイル上限を要求します。署名と予約を先に暗号化保存し、その後で送信開始状態も保存します。

書込み失敗は成功扱いせずロックします。ファイル置換後の同期障害は保存結果が不確定なので、必ず旧状態へ戻るとは言いません。送信後の応答を失っても、新しい支払いを作りません。送信開始後のロックは、ネットワークへ渡した署名を無効化するものではありません。古いセッションの遅い応答は新しい解除セッションへ書き戻しません。

同一保管庫内のsequence予約と同じ依頼キーの整合を維持します。別キーは別の支払いです。古いバックアップや別端末、別アプリまで一括で拘束する仕組みはなく、古いバックアップ復元は支払い取消しではありません。

未解決の同一口座・ネットワークは新規署名を保留します。安全な予約解放・再送・置換・アーカイブ・マルチデバイス回復は未実装です。履歴上限128件に達したら自動で履歴を捨てず拒否します。

## 観測と証明
StellarはHorizonのenvelope/result/操作/ledgerを照合します。SCP認証、独立した歴史残高差分は検証しません。
AptosはRESTの署名・version/hash・歴史的残高/sequenceを照合します。LedgerInfo署名・accumulator・state proofは検証しません。手数料以外の追加refund等で期待差分と一致しなければ受取済み表示にせず停止します。
両方とも `finalityProven:false` です。ブリッジ解放、無人の確定入金判定などに使用しません。

## 検証範囲
新規HTTP試験は実Ed25519署名とワイヤ形式を検査する二つの合成サーバーです。二つのURLは同じ合成台帳を共有し、実Stellar Core/Aptos VMではありません。ブラウザの追加画面は合成APIによるDOM試験で、実HTTP/CSPの統合を証明しません。フル検証では実Stellar/Aptosゲートを明示的にblockedにしています。

既存のBitcoin Core/Anvil/LiteSVM回帰試験は別枠です。それらの成功をStellar/Aptosの実行成功へ数えません。正式0.8.24と固定nightly AMMも区別します。
