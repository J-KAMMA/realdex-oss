# RealDEX v0.16 — Stellar / Aptos ローカル送金

## 目的と対象
Stellar StandaloneのXLMと、Aptos local chain ID 4のAPTを、所有者確認・署名・保存・初回送信・再照合まで接続した開発版です。実Stellar Core・実Aptos VMとの適合試験は未実施です。新機能のHTTP試験では実署名を検査しますが、台帳と残高更新は合成モデルです。

**未監査。実資産・本番資産の秘密鍵を使わないでください。** 新規の使い捨て試験口座だけを使用します。localhostという接続先だけでは、その先が本番へ中継されていないと証明できません。

## 更新と起動
旧プロセスを正常終了し、暗号化バックアップを別保存してから、このZIPを新しいフォルダーへ展開します。旧版を実行したまま同じ保管庫を書き換えないでください。

```sh
node app/cli.mjs start
# ウォレット単独の従来の保存先を使う場合:
node wallet/cli.mjs start
```

前者の既定保存先は `~/.realdex-app/`（walletとnodeを分離）、後者は `~/.realdex-wallet/` です。自動移行しません。追加ローカルサービスはNodeの組込み機能で起動し、npm installは不要です。これは元のReactアプリ全体のビルド成功を意味しません。

ターミナルに表示される `#key=` を含む所有者専用URLを同じPCで開きます。このURL、パスワード、バックアップ、署名済みデータをAIや共有ノードへ渡さないでください。新しい口座は暗号化バックアップを作成し、ファイルを読み戻して検証するまで署名できません。

## ローカルネットワーク設定
別途、自分で管理するHorizon＋Stellar Standalone、またはAptos local nodeを起動します。この版はそれらのインストール・起動を自動化しません。送受両口座をローカル側で作成・資金準備しておく必要があります。

読取り専用CLIで、指定したチェックポイントを収集できます。

```sh
node wallet/non-evm/account-config.mjs --family stellar --rpc-url http://127.0.0.1:8000/ --rpc-url http://127.0.0.1:8001/ --checkpoint-height 1 --output stellar-local.json
node wallet/non-evm/account-config.mjs --family aptos --rpc-url http://127.0.0.1:8080/v1/ --rpc-url http://127.0.0.1:8081/v1/ --checkpoint-height 1 --output aptos-local.json
```

ポートと高さは実環境へ合わせて変更してください。Stellarは末尾 `/`、Aptosは `/v1/` です。2〜4件の異なるURLが必要です。同じノードの二つの入口も設定できますが、独立ノードの合意とは数えません。

CLIは設定を新規ファイルへ保存するだけで、署名・送信・ウォレット設定変更をしません。既存ファイルへの上書きも拒否します。**収集したhashは、CLIが独立認証したものではありません。** 管理しているノードのログ等、別の経路で照合してください。収集結果の `independentlyTrusted` はfalseです。

生成設定の `broadcastEnabled` はfalseです。初回送信も試す場合は、取込前にJSONを点検し、使い捨てローカル環境に限ってtrueへ変更します。`maxTransferAtomic`、`maxFeeAtomic`、`minConfirmations` も確認します。これらの上限は今回のオンライン経路に適用されるローカル方針で、オンチェーンの資金制限ではありません。

ウォレット内の「Stellar / Aptos・所有者のオンライン送金」の設定欄へJSONを貼り、次を全文入力して登録します。

```text
ADD stellar:standalone <checkpoint hash>
ADD aptos:local-4 <checkpoint hash>
```

設定保存時にロックし、古い要求を無効化します。保存失敗時には設定状態が不確定として再起動が必要です。登録済みネットワークの置換・削除UIは未実装です。設定ファイルを稼働中に手動編集しないでください。

## 送金
ネットワークとローカル鍵の口座を選び、受取先の完全なアドレス、数量、支払いキーを入力します。

StellarはXLMの小数数量、手数料をstroops、任意のUTF-8テキストmemo（28byte以下）で指定します。送信元の最低残高、売り注文による拘束量、手数料を残して送金できるかを検査します。通常のGアドレスと単一マスター署名に限定し、新規口座作成、MUXED、マルチシグ、Soroban、発行トークンは扱いません。

AptosはAPTの小数数量、最大ガス単位、ガス単価（octas）を指定します。送信元の認証鍵、sequence、利用可能残高を取得し、公開鍵とゼロ署名だけを使ってシミュレーションします。初期のEd25519認証鍵と既存の送受口座、固定の `0x1::aptos_account::transfer` だけに限定しています。鍵ローテーション、アカウント抽象化、任意関数、任意トークンは未対応です。

「承認待ちへ」を押しただけでは署名しません。別の確認カードで受取先全体、金額、sequence、期限、費用、チェックポイント、設定のfingerprintを確認し、受取先を全文再入力します。送信チェックは既定でOFFです。チェックなしでは署名・暗号化保存だけを行います。

初回送信を別操作で行う場合は、履歴の該当取引IDを全文再入力します。署名時と初回送信直前に再検査し、期限・sequence・鍵・残高が変わった場合には停止します。署名済みバイト列を勝手に更新しません。

## 通信断と再照合
署名とsequence予約を保存し、さらに送信開始前の「結果不明」状態を保存してから、署名済みデータを送出します。保存失敗では送信しません。送信が始まった後のロックは、その取引の取消しにはなりません。

同じ支払いキー・同じ内容なら保存済み記録を返し、別の支払いを作りません。同じキーで内容を変更すると拒否します。違うキーは別の支払いなので、同じ請求を別キーで申し込んだことまでは検出しません。

未解決の記録がある間は、同じ口座・ネットワークの新規オンライン署名を保留します。オフライン経路を使ってこの保留をすり抜ける要求も署名段階で拒否します。既存の古いオフライン署名が未解決の場合もオンライン署名を止めるため、この機能の試験には新しい口座を使ってください。

再照合は読取りのみです。送信受付・通信断後の自動再送、別sequence、期限延長、再署名、予約の手動解除、取消し・置換は未実装です。期限切れだけでは未解決記録を消しません。

Stellarは保存したenvelope、transaction/result XDR、操作内容、費用、収録ledgerを照合しますが、前後の口座残高差分の証明はしません。Aptosは保存した署名・固定payload・取引versionと、その直前／直後の残高・sequenceをRPCから照合します。どちらも `finalityProven:false` の観測値です。ブリッジの資金解放には使用しません。

## 再現デモと試験
外部チェーンや実鍵を使わない合成HTTPデモです。

```sh
node wallet/non-evm/account-demo.mjs
node --test --test-concurrency=1 --test-reporter=tap wallet/test/account-online.test.mjs wallet/test/account-transport.test.mjs
node app/verify.mjs --full --output acceptance-new
```

最後のコマンドは、欠けた依存や未実装の実Stellar/Aptos検証をblockedとし、成功終了しません。オフラインDOM画面試験を実ブラウザのHTTP/CSP試験へ昇格させません。

## バックアップと制約
新しいオンライン履歴・設定は旧アプリで読めません。更新後の同じ保管庫を旧版で上書きしないでください。通常再起動と現在の記録の読み戻しは検査していますが、古いバックアップの復元・別端末による重複署名を一括制御する仕組みはありません。古い状態へ戻す操作は署名済み取引の取消しではありません。

非EVMの保存履歴は従来どおり最大128件です。履歴の自動削除や安全なアーカイブ移行は未実装です。ルートの依存環境、実Stellar/CoreとAptos VM、公開テストネット、Windows/OS鍵保護、独立監査が残ります。
