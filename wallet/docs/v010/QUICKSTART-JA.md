# RealDEX v0.10 本番前ハードニング版 — 起動・更新・検証

日付: 2026-09-05 / release: `0.10.0-dev.20260905`

**本番公開版ではありません。未監査で、実資産を入れないでください。** 今回は保管庫のロック競合、容量不整合、保存障害、子プロセスへの認証情報の引継ぎを修正しました。メインネットや非EVM送信の対応範囲は広げていません。

## 1. 起動

ZIPを別の空ディレクトリへ展開し、`app/`、`wallet/`、`node/`のある場所から実行します。

```sh
node app/cli.mjs start
```

追加層の通常起動に `npm install` は不要です。検証した実行環境はLinux x86-64、Node 22.16.0です。Windows実機・OSの鍵保護は未検証です。

一括起動の既定データ保存先は `~/.realdex-app/` で、その中のwalletとnodeを別プロセス・別ディレクトリで使います。端末に表示されるウォレット専用URLには所有者の権限が含まれます。AI、他人、共有ノードへ渡さないでください。共有ノードの画面は `http://127.0.0.1:8787/node/` です。

従来の `~/.realdex-wallet/` を使う単独起動は、引き続き次のコマンドです。一括起動とは保存先が違います。

```sh
node wallet/cli.mjs start
```

認証トークン・鍵を設定したシェルから起動しても、一括起動はそれらを子サービスへ自動転送しません。PATH、HOME等の必要最小限のみ引き継ぎます。独自のプロキシ・認証環境変数が必須の構成は別途レビューが必要です。検査を通す目的で転送制限を解除しないでください。

## 2. 旧版から更新する前に

1. 旧版でまだ解除できる間に、暗号化バックアップを保存し、バックアップ内の口座一致を検証してください。AI権限を止めてからロックし、正常終了します。
2. 保管先全体と旧版ZIPは別に保持し、新版はコード用の空ディレクトリに展開してください。秘密データをソースやGitへ入れないでください。
3. 同じ保存先に二つのウォレットを同時に起動しないでください。新規復元は空の保存先で実施し、口座を確認してから利用します。

v0.9の通常サイズの保管庫スキーマは変更していません。ただし、この版は**既に容量不整合で読めなくなった旧版のファイルを自動修復しません**。その場合、元ファイルを編集・削除せず保全し、正常な暗号化バックアップを使う復旧と、送信履歴の照合を別に行います。古いバックアップへの巻戻しは、nonce・AI予算・取引履歴の巻戻しにもなり得るため、無条件に送信を再開してはいけません。

異常終了後の `writer.lock` は自動削除しません。他の実行プロセスがないこととデータ保全を確認せずに削除しないでください。PIDだけで他プロセスを強制終了する処理もありません。

## 3. 修正後のロック・容量の動き

解除や署名が順番待ちでも、所有者がロックすると、そのロック以前の要求は失効します。HTTPで受信途中だった解除要求も、ロックをまたいで有効になりません。失効した操作は、新しい状態を確認してから改めて依頼します。

保管庫の暗号化前データ上限は450,000バイトです。秘密鍵だけでなく履歴なども含みます。上限超過では保存を拒否してロックし、直前の読める保管庫を維持します。履歴を黙って消したり、AI予算をリセットしたりはしません。自動アーカイブ・無制限の履歴保管は未実装です。

## 4. ローカル検証

診断だけを行うコマンド:

```sh
node app/cli.mjs doctor
```

選択試験とソース整合性を確認するコマンド:

```sh
node app/verify.mjs --output acceptance-selected-new
```

全体ビルド・実EVM・実ブラウザまで要求するコマンド:

```sh
node app/verify.mjs --full --output acceptance-full-new
```

出力先は存在しない新しいディレクトリを指定します。`acceptance.json` の `gates`、`selectedScopePassed`、`fullLocalAcceptancePassed` を確認してください。`blocked` / `not-run` / `failed` は合格ではありません。全体未達では終了コード2、選択範囲が不合格なら終了コード1です。

選択試験の成功は、実チェーンでの送信成功や本番承認を意味しません。実ブラウザが管理ポリシーで止まる場合も、オフライン描画の成功で代替しません。

## 5. 正規のビルド・コンパイラ環境

既存ルートプロジェクトの固定指定はNode 24.14.0 / pnpm 11.25.0です。依存指定・lockfileは今回変更していません。インターネットへ正常に接続できる隔離検証環境で、固定バージョンを用意します。

```sh
pnpm install --frozen-lockfile --ignore-scripts
```

依存のインストールスクリプトが必要になった場合は、対象をレビューしてください。取得や実行に失敗したまま合格へ進める仕組みはありません。

`integration/compiler-pin.cjs` が定める公式Linux x86-64 Solidity 0.8.24バイナリを、SHA-256確認後に設定します。バイナリはZIPに同梱していません。

```sh
export REALDEX_SOLC_BINARY=/absolute/path/to/verified-solc
node integration/compile-local.mjs --compiler "$REALDEX_SOLC_BINARY" --output compilation-new
node app/verify.mjs --full --output acceptance-full-new
```

コンパイラ入力・コード同定資料を生成する実装を追加しましたが、今回の環境ではバイナリを取得できず、その成功経路は未実行です。実EVM試験も未実行です。欠落時に別バージョンへ自動変更しません。

## 6. 実ブラウザ・CI

`integration/browser-requirements.txt` は隔離したPython仮想環境用です。実ブラウザ試験は、本物のローカルHTTP、保管庫、鍵生成、暗号化バックアップ、CSPを使い、公開RPCや実資産を使いません。

```sh
python3 wallet/test/browser-http.py --output browser-http-new
```

必要なら `--executable /absolute/path/to/chromium` を指定します。今回の環境ではHTML応答までは確認できましたが、ブラウザの接続は管理ポリシーで遮断されました。ブラウザの制限を無効化して合格させる処理はありません。

`.github/workflows/local-acceptance.yml` は手動実行・pull request用のCI定義です。checkout/setup-nodeをコミットSHAへ固定し、読み取り権限のみ、デプロイ・公開・実資産操作は含めていません。このCI定義のGitHub上での実行・成功は未確認です。

## 7. AIと送信の範囲

AIは既存の制限付き送金・preview等の範囲のままです。ウォレット解除、鍵出力、予算変更、任意署名、承認、swap、bridgeを許可していません。所有者の5分無操作でロックし、AIからのアクセスで延長しません。再解除後の権限再有効化も所有者操作です。

チェーン候補数と送金対応数は別です。非EVM送信、ブリッジ実行、OSの鍵保護、Windows配布、独立監査などは未達です。詳細は以前の [v0.9操作手順](../v09/QUICKSTART-JA.md) と本版の [開発報告](DEVELOPMENT-REPORT-JA.md) を参照してください。
