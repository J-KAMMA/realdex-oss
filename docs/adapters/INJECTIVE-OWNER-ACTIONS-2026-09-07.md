## Two implemented owner routes

POST `/api/non-evm/injective/cancel/prepare` takes:

```json
{
  "accountId": "existing-local-evm-account-id",
  "sourceRecordId": "confirmed-create-order-record-id",
  "payment": {
    "requestKey": "unique-cancel-request",
    "orderHash": "0x...64 lowercase hex digits...",
    "policy": {
      "gasLimit": "1000000",
      "gasPriceAtomic": "500000000",
      "maxGasFeeAtomic": "500000000000000",
      "gasMarginBps": 12500,
      "timeoutBlocks": 40,
      "maxAgeMs": 30000
    }
  }
}
```

The source must be an existing confirmed *create-order* record owned by the same
local EVM key. Endpoint, market, subaccount, client ID, original quantity and
limit price come from its retained review. A same-height v2 open-order query must
match the requested order hash AND all those fields. An unrelated or absent order
does not become a cancel target merely because a client supplies a hash.

POST `/api/non-evm/injective/withdraw/prepare` takes:

```json
{
  "accountId": "existing-local-evm-account-id",
  "payment": {
    "requestKey": "unique-withdraw-request",
    "endpoint": "http://127.0.0.1:PORT",
    "subaccountId": "0x...own nondefault subaccount...",
    "denom": "ubase",
    "amountAtomic": "1000000000000000000",
    "policy": {
      "gasLimit": "1000000",
      "gasPriceAtomic": "500000000",
      "maxGasFeeAtomic": "500000000000000",
      "gasMarginBps": 12500,
      "timeoutBlocks": 40,
      "maxAgeMs": 30000
    }
  }
}
```

The integers above are diagnostic examples, not current gas recommendations.
Withdrawal is exchange subaccount -> SAME owner's bank balance. No arbitrary
recipient, external transfer or bridge destination is accepted. Nondefault
subaccounts only; no implicit/default-subaccount heuristics. Ownership follows
the full subaccount prefix and the compressed public key's Ethereum-style address.
Spendable exchange balance is floored to whole atoms; locked `total` funds are
not treated as available. Gas is paid from bank INJ BEFORE the withdrawal; funds
expected from the withdrawal cannot pay its own gas.

All routes retain the existing UI capability/origin checks. Public endpoints,
other hosts, mainnet, credentials, ambiguous amounts and unknown input fields
are rejected. The UI requires a local EVM account, separates cancel and withdraw
inputs and displays the exact action, source/target, quantity, fee and review SHA.

## Exact signing and durability

The new `realdex.injective-owner-action-review.v1` is generated by the owner
service, not an indexer. It includes account/sequence, anchor, observed target
state, fee policy, unsigned transaction and simulation. A self-hash is only a
consistency check. The validator independently rebuilds MsgCancelSpotOrder or
MsgWithdraw, TxBody, AuthInfo, SignDoc and empty-signature simulation bytes.
A rehashed review with different bytes, sender/destination, fee or timeout fails.

Existing `/api/non-evm/approve` requires the full review SHA and `broadcast:false`.
It signs once, saves the complete TxRaw and deterministic transaction hash inside
the encrypted Vault and does NOT transmit. Display fields and actual signed
bytes are validated again when history is loaded.

The existing submit route requires a SEPARATE full tx-hash confirmation.
Before transmission the service rechecks account number/sequence, available
funds, gas and target state, and persists `broadcast-unknown`. Save failure locks
the Vault and emits no transaction. A final expiry check occurs both after
recheck and after durable save. The latter may leave a conservative unknown even
when transmission did not begin. No automatic record deletion, unlocking or
retry is introduced.

Invalid reports are validated on a copied record BEFORE replacing in-memory history. A rejected height/hash/effect/authority field leaves both encrypted storage and in-memory state unchanged. This also corrects a reproduced INJ-05 observation-update defect.

Cooperating API operations are serialized. The Vault additionally checks for
unresolved Injective transactions inside its serialization boundary. Cancel and
withdraw share the same owner-key sequence guard as order creation.

A cancellation may observe MORE partial fills before signing/submission: only
a smaller remaining quantity is allowed. The authorization means “cancel the
remaining portion of THIS order”, never reverse past fills. An increased
remainder, changed original order or missing target blocks transmission.
A signed operation which later cannot be submitted stays reserved. Safe expiry/
abandonment and proof-backed recovery are separate unfinished work; do not
delete records to bypass this boundary.

## Receipt versus effect

After uncertain transmission, lookup uses the saved transaction hash only.
It never retransmits, creates a new sequence or signs a replacement. Terminal
records return idempotently without repeated mutation. Explicit CheckTx rejection
remains terminal; HTTP errors/not-found retain uncertainty.

Successful inclusion can optionally carry a SEPARATE `actionEffect` observation
from the same node at the included height: order presence for cancel; bank and
deposit balances for withdraw. If these reads fail, `status: unavailable` is
retained alongside the included transaction. This is not a before/after causal
proof, quorum check, finality proof or public settlement assertion.
`independentProof` and `finalityProven` remain false. Terminal effect-unavailable
records are not automatically re-read; a separate evidence refresh is not yet
implemented.

The new real-node scenario creates a 2-unit order through WalletServer, fills
0.5 using a disposable counterparty, cancels the remaining 1.5 through owner
APIs, deposits fictitious base via test setup, rejects a one-atom excess
withdrawal before signing, then submits a proper owner withdrawal while
deliberately losing its HTTP response. A fresh process reopens the encrypted
Vault, rejects resend and reconciles its saved hash. Bank and deposit balances
and exact gas debits are checked. Setup deposit/counterparty use diagnostic
fixture signatures, not newly exposed production APIs.

Synthetic tests cover amounts, bound target/display/bytes, unsafe destination,
available-vs-total balance, shared-key uncertainty, persistence failure, rejected/
lost/not-found responses, concurrent submission and expiry races. Python
independently reconstructs protobuf and Decimal gas costs from original review
fields. DOM tests use synthetic responses and do not constitute real browser
wallet/chain end-to-end execution.

The source/real-runtime/browser counts, exact tested tree and raw log hashes are
in the delivery report. No full-runtime matrix or production release is inferred
from this focused local-node work. No speedup claim is made.

## Protocol basis and limitations

The implementation uses the already pinned v1.20.3 local-node behavior.
Official description of MsgWithdraw sending exchange funds back to Sender:
https://docs.injective.network/developers/modules/injective/exchange/04_state_transitions

Only trusted local Linux diagnostic nodes and fictitious funds were tested.
No public testnet/mainnet, independent state proofs, remote signer, OS key
isolation, Windows support, independent audit or source-rebuilt upstream binary
is certified here. Existing 64-entry encrypted Injective journal capacity and
password-backup requirements remain. Local snapshots/REST headers cannot
authenticate a malicious chosen node or prevent a privileged whole-Vault rollback.
