# IBCブリッジの安全性と未達

## 預かり・権限

RealDEX運営者にミント鍵、出金承認鍵、共有預かり契約を追加していません。ネイティブIBCモジュールがロック・バーン・ミント・返金を行います。利用者は自己管理鍵でMsgTransferへ署名します。元来のチェーン・IBC・light clientの安全性、利用者が設定したcheckpointとlane、ノード実装に依存します。

送信許可は所有者のみです。AI／共有ノード／外部アプリに新規署名APIを公開しません。端末のロックは既に送った取引、パケット、他端末の署名を無効にしません。

## 実証した範囲と証明できないこと

実行試験では2つの別プロセス・別状態・別genesisの単一validatorチェーンを作り、本物のTendermint clientsとconnection/channel handshakeを行いました。中継は実state proofと署名付きヘッダーを送り、IBCノードが検証します。偽のクライアント、無条件のproof verifier、直接残高を書き換える橋は使いません。

一方、デスクトップはまだTendermintのvalidator set・コミット・アプリケーション状態証明を独立検証するライトクライアントではありません。取引包含を、RPCが報告したdata rootに対して検査し、イベント・残高差分も照合しますが、悪意ある同一情報源による偽造の可能性を排除しません。2つの観測URLが独立した管理主体とも限りません。報告は常に `finalityProven:false`。本番用の決済証明や別プロトコルの資金解放条件には使用しません。

診断用ノードは固定したPR CI成果物です。安定版認定、ソースからの再現ビルド、独立監査を済ませたものではありません。SHA-256は同一性の検査であり、バイナリが安全である証明ではありません。

## 返金と停止

時刻が過ぎただけでは返金されません。未受取のproofがノードに認められ、MsgTimeoutが処理される必要があります。受取済みパケットについて未受取証明は成立しません。エラーACKも元チェーンで処理して初めて返金されます。源泉の送信手数料と中継費用は戻りません。

チェーン停止、light client期限切れ、証明履歴のpruning、中継者不在などは返金・受取を遅らせたり阻害します。自動・即時・必ず回収できるという保証はありません。通常画面は中継サービスを起動しません。実行用中継器は使い捨て試験専用です。

返金と受取のbalance差分はブロック単位で照合します。同じブロックに別の入出金があると、正しい移転も未確認とする場合があります。複数メッセージを束ねた中継取引は保留します。これを理由にもう一度同じ資産を送ってはいけません。

## 保存・復元

署名とsequence予約は暗号化ファイルへ保存してから送信します。同じキーの再要求で別署名を作りません。結果不明は保持し、期限・手数料・sequenceの自動置換を行いません。RPCから記録が消えたときに「失敗して返金された」と推測しません。

現在の保管庫をまたぐロールバック・複数端末の二重署名問題は未解決です。古いバックアップへ戻しても過去の署名能力は消えません。最新バックアップの読み戻し試験は、この問題の解決ではありません。旧版による新規IBC履歴の上書きを避けてください。

## 明示的な未対応

公開IBCレーン、EVM/BTC/Solana間ブリッジ、独自wrapped asset、IBC v2/Eureka、複数hop／hooks／PFM、常駐中継、集中型サービス課金、AI自動ブリッジ、予約解除／自動再送は未対応です。CCTPの既存リリース停止条件は解除していません。元React全体ビルド、正式コンパイラ、実ブラウザHTTP/CSP、Windows、OS鍵保護、第三者監査の合格をこの追加で代替しません。
