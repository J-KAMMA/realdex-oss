# RealDEX universal architecture

Status: extensible capability registry installed, 2026-09-01. This is not a claim that every chain, wallet, token, pool, or route is executable today.

## Goal

RealDEX should be able to add any chain, wallet, and fungible token without rewriting its safety model. “Universal” therefore means open-ended discovery and adapter contracts, while execution remains specific and fail-closed.

```text
CAIP-2 chain identity
        ↓
wallet capability negotiation
        ↓
CAIP-19 asset identity + provenance
        ↓
venue / pool / bridge discovery
        ↓
fresh quote + simulation + balance + fee checks
        ↓
explicit approval / transaction signing
        ↓
submitted → included → confirmed/finalized → product completion
```

CAIP-2 supplies a namespace-qualified blockchain identifier, preventing one ecosystem’s numeric chain ID from being mistaken for another. CAIP-19 extends that identity to native assets, fungible tokens, and individually addressed assets. EIP-6963 supplies race-resistant discovery for multiple injected EIP-1193 providers. Wallet Standard supplies discoverable wallet interfaces, while chain-agnostic wallet sessions can negotiate exact chain, account, method, notification, and capability scopes. Sources: [CAIP-2](https://standards.chainagnostic.org/CAIPs/caip-2), [CAIP-19](https://standards.chainagnostic.org/CAIPs/caip-19), [CAIP-25](https://standards.chainagnostic.org/CAIPs/caip-25), [EIP-6963](https://eips.ethereum.org/EIPS/eip-6963), [Wallet Standard](https://wallet-standard.github.io/wallet-standard/) (reviewed 2026-09-01).

## Components

### Chain registry

Each entry owns a CAIP namespace, address model, wallet interface, operation-specific readiness, and operation-specific adapter IDs. Swap verification, swap execution, bridge execution, and finality tracking cannot overwrite one another with one ambiguous namespace adapter. A namespace entry is not an executable chain. Exact network identity, RPC, bytecode/program/module identity, finality, fee currency, limits, and incident policy belong to a separately reviewed adapter revision.

### Wallet capability registry

Wallets are classified by capabilities rather than brand names. Connection, message signing, approval, transaction signing, and broadcasting remain distinct grants. The app requests only the chain and methods needed for the selected action; it must invalidate quotes and permissions when the account, network, or session changes.

### Live Wallet Standard discovery

The Universe Wallets view listens for Wallet Standard registration events and announces app readiness after installing its listener. It handles wallets loaded before or after the view, deduplicates by object identity rather than brand name, and removes entries on unregister. Names, reported chain identifiers and feature names are inspection metadata only. Passive discovery never reads accounts or icons, calls connect/sign/broadcast methods, selects a wallet, creates a grant, or changes an executable route. The separate optional Solana connection action below is explicit and registration-bound.

Supported metadata is bounded to Wallet Standard version 1.0.0, 32 wallet objects, 64 chains and 64 feature names per object, 80-character names and 160-character identifiers. Control/bidirectional-override characters, malformed or duplicate identifiers and throwing metadata are rejected. Reported identifiers are not assumed to be CAIP-2 networks: for example, `solana:devnet` is shown verbatim, not converted into a genesis-hash identity. Unknown namespaces and features remain self-reported metadata, not executable support.

Passive discovery invokes only the optional `standard:events` change subscription. On change, public metadata is re-read; payload accounts are ignored. Without a valid subscription cleanup function the display says snapshot-only. A replaced event method or invalid changed metadata removes the entry until re-registration; fresh feature wrapper objects with the same event method are accepted. Page-local IDs distinguish same-name registrations but are not identity proofs. Unmounting removes listeners/subscriptions; stale callbacks and old unregister handles cannot replace a newly registered entry. No wallet metadata is persisted.

Discovery browser QA uses synthetic registrations in an extension-free profile, with account/icon getters and transaction methods configured to fail if accessed. Widths 1280/390/320px, long identifiers, duplicate names, 200% text, keyboard focus, change notifications and unregister are covered. This does not establish compatibility with every real wallet, enable native Wallet Standard transactions, or replace the existing Circle Solana provider adapter. Real-wallet authorization and reviewed exact-chain execution remain separate work.

Sources reviewed 2026-09-02: [Wallet Standard registration protocol](https://github.com/wallet-standard/wallet-standard/blob/master/packages/core/base/src/window.ts), [wallet metadata contract](https://github.com/wallet-standard/wallet-standard/blob/master/packages/core/base/src/wallet.ts), [change events](https://github.com/wallet-standard/wallet-standard/blob/master/packages/core/features/src/events.ts).

### Explicit Solana Wallet Standard connection sessions

`src/wallet/solana-standard-session.ts` provides a connection-only API for a deliberately selected wallet object. `SolanaStandardConnectionPanel.tsx` exposes it under Universe > Wallets > Optional Solana account connection. The callable discovery controller retains the exact registered object privately and invalidates all its connections and pending observations on removal or teardown; registering that object again cannot revive old connections. This is not an executable swap adapter. Separate release and transaction approval are still required before any signing implementation is introduced.

The API maps the three documented public-cluster CAIP identities to their Wallet Standard `solana:mainnet`, `solana:devnet`, and `solana:testnet` identifiers. This mapping is not a live RPC or genesis verification. Unknown/custom/local clusters reject rather than being guessed. It requires v1 connect/change/sign-transaction interfaces and an explicit supported transaction version. Only change subscription and `connect({ silent: false })` are invoked; signing, broadcasting, wallet disconnect, icon reads, silent restoration and persistence are absent.

After connection, returned accounts must match the wallet's current accounts. Each public key must be exactly 32 bytes and encode to the stated address; account chain/feature scopes must be subsets of the wallet's reported scopes. No account is selected automatically. Explicit account/version selection yields a page-local, five-minute binding with execution/signing/submission all false, not a route execution grant. A clone, mutation, replaced selection, changed method, changed scope/account set, clock rollback or expiration cannot pass current-binding verification.

The change subscription is installed before connecting. Normal account-change notifications emitted by connect itself are accepted only when the final snapshots agree; a change during final snapshot validation rejects, and any subsequent event invalidates the session. Connection overlap is excluded per wallet before invoking its methods. A new explicit connection attempt supersedes the previous session for that wallet; disposing an old session cannot invalidate the new one. Timeout/cancellation ignores late responses but cannot close a wallet prompt, so exclusion remains until the original promise actually settles. Local dispose removes listeners and invalidates bindings; it does not claim to revoke wallet permissions.

Wallet registration, exact public network, account and transaction format start unselected. Only Request account access contacts the chosen wallet. Keep account selection creates a local binding and enables no route, quote, signing or submission. Editing an account or format clears the previous binding; changing a wallet or network disposes the entire connection. Stop waiting aborts only local observation, and Forget local connection does not revoke wallet permission. Neither operation invokes wallet disconnect. The UI checks notifications immediately, silently changed metadata/accounts every second, and the exact five-minute expiry deadline; every API selection also revalidates synchronously. Raw provider errors are not displayed.

Verification uses simulated wallets only, including registration removal during a pending request, re-registration, cancellation/late responses, same-name registrations, exact expiry and silent mutation. `qaSolanaStandardConnection.mjs` exercises explicit connection and selecting the second account with version 0 in a fresh browser profile at 1280/390/320px and 200% text; all external HTTP requests are blocked and signing/disconnect/icon access is forbidden. Real-wallet compatibility, live genesis reads, transaction signing, signed-byte validation/recovery integration and broadcasting remain separate work. Sources reviewed 2026-09-02: [standard connect](https://github.com/wallet-standard/wallet-standard/blob/master/packages/core/features/src/connect.ts), [Solana signing interface](https://github.com/anza-xyz/wallet-standard/blob/master/packages/core/features/src/signTransaction.ts), [cluster identifiers](https://github.com/anza-xyz/wallet-standard/blob/master/packages/core/chains/src/index.ts), [Solana CAIP identity profile](https://namespaces.chainagnostic.org/solana/caip2).

### Cosmos injected wallet connection session

`src/wallet/cosmos-injected-session.ts` adds an API-only connection boundary for a deliberately supplied Keplr-compatible provider and exact Cosmos chain profile. A profile must bind one `cosmos:*` CAIP-2 identity to the identical wallet chain ID and one lowercase bech32 prefix. The connection invokes only `enable(chainId)` and `getKey(chainId)`; it never reads an offline signer, `signDirect`, `sendTx`, or another signing/broadcast capability. The published Keplr type surface defines `enable`, `getKey`, and the returned name, algorithm, public key, raw address, bech32 address, and hardware flags. Source reviewed 2026-09-02: [Keplr published TypeScript interface](https://app.unpkg.com/@keplr-wallet/types@0.12.278/files/src/wallet/keplr.ts).

The returned key must be a compressed 33-byte secp256k1 public key. RealDEX independently derives `RIPEMD160(SHA256(pubkey))`, requires it to equal both the 20-byte raw address and decoded bech32 payload, and requires the exact reviewed prefix. Two consecutive key reads must agree after connection. A `keplr_keystorechange` event invalidates immediately when available, but because the current official event documentation was not retrievable during this review, every later current-binding assertion also calls `getKey` and rejects silent changes, method replacement, session supersession, expiry, or clock rollback.

Explicit account selection creates only a frozen five-minute page-local binding with signing, submission, and execution disabled. Connection timeout or local cancellation does not claim to close the wallet prompt; the provider remains excluded until its original request settles, and a late result cannot create a usable session.

The Universe Wallets view now has an optional connection-only panel for a detected `window.keplr` provider. Provider and reviewed testnet profile are blank until explicitly selected, and the provider is not called until **Request account access**. Noble `grand-1`/`noble` and Osmosis `osmo-test-5`/`osmo` are the only profiles exposed. After validation, the single returned account is shown for review but is not selected until **Keep this account selection**. Forgetting removes only RealDEX page state and does not claim to revoke wallet permission.

Component tests use synthetic providers and forbid reading signing or broadcast properties. `qaCosmosInjectedConnection.mjs` repeats the explicit flow in an extension-free browser profile at 1280/768/375/320px and 200% text, blocks every external request, verifies 44px controls, keyboard focus, no horizontal overflow, and `keplr_keystorechange` invalidation. This is not real-wallet compatibility evidence, live genesis verification, signature permission, signing, broadcasting, or route enablement, so the Cosmos registry remains `partial`.

### Cosmos injected pre-signing preparation boundary

`src/swap/cosmos-injected-signing-preparation.ts` joins a genuine current Cosmos injected account binding to a genuine in-memory source-bound Osmosis verification. The source-bound result and preparation are identity-branded capabilities: JSON imports, structural clones, forged fields and post-verification mutation are rejected. Before a result can be prepared, the unsigned TxRaw public key must be a valid secp256k1 curve point, derive the exact authority through `RIPEMD160(SHA256(pubkey))`, equal the wallet binding public key, and match the exact chain/account identity.

The preparation re-hashes the complete unsigned TxRaw and canonical intent, checks the source/destination amounts and source/route/read-policy provenance, and revalidates both the wallet account and source-bound evidence after asynchronous hashing. It fixes the authority, recipient, chain, wallet chain ID, public key, hardware metadata, venue execution target, denoms, amounts, account number, sequence, fee, gas, timeout height and sign-document hash into a frozen page-local review package. Its expiry is the earliest of the wallet binding, quote, signed route manifest and signed read policy; the live clock is checked again after asynchronous work.

The package contains no signer, signing method, RPC reader, storage writer, broadcaster, signed bytes or resend authority. `requiresFreshVerification` stays true and signing, broadcast and execution remain false. A future explicitly authorized signing action must freshly revalidate the package and show its exact summary; it cannot treat this preparation as signing permission.

### Cosmos signed observation persistence

`src/swap/cosmos-signed-swap-journal.ts` persists bounded metadata from genuine in-memory signed-swap evidence. One slot is keyed by chain ID, canonical authority and uint64 sequence, deliberately independent of wallet, session, venue, account-number claims and quote. An exclusive native Web Lock covers read/check/write/exact readback. The first record wins; the exact same signed transaction and review intent is idempotent across sessions, while a competing transaction or intent is rejected without overwrite. Unavailable locks/storage, corrupt records, quota failures and readback mismatches fail closed. No expiry, deletion or retry path clears the slot, including after an uncertain write outcome.

Restored records say `signed-observed` and `submissionStatus: unknown`: local history cannot prove the transaction was never submitted elsewhere. They contain no transaction bytes, signatures or session data, and grant no signing, submission, execution or automatic resend authority. A checksum detects accidental changes but is not authentication against same-origin script or a user modifying storage. A missing record is not permission to execute. The journal supports the pre-signature reservation below, but submission transport, global nonce coordination and finality reconciliation are still unfinished. Browser eviction/clearing, other profiles/devices/origins and uncooperative writers remain outside its protection. Future signing/submission orchestration must use explicit reservation and fresh network/account reconciliation before enabling execution.

The lock boundary follows the [W3C Web Locks draft](https://www.w3.org/TR/web-locks/) (reviewed 2026-09-02): cooperating contexts share locks within a storage bucket, not across profiles/devices. `scripts/qaCosmosSignedJournal.mjs` checks native two-tab exclusion, release after tab closure, reload of synthetic metadata, clone rejection and corrupt-history rejection. Genuine evidence creation and journal persistence/conflict/error paths are separately covered by the synthetic Cosmos source integration tests. No production wallet or transaction is used.

### Cosmos pre-signature reservation

`reserveCosmosInjectedSigning` holds the same slot lock across fresh account-binding checks and creation of a genuine signing preparation. Caller-owned selectors and intent are snapshotted before the first await. Any occupied slot, including an identical reservation, signed observation or malformed history, blocks another reservation. After preparation, history is checked again before saving bounded `signing-reserved` metadata and verifying exact readback. The account, source-bound evidence, live expiry and stored record are checked once more before returning. Post-write failure leaves the reservation intact. The returned preparation still has signing/broadcast/execution disabled: reservation is not human confirmation or signing authority.

The reserved record stores hashes, timestamps and the session-bound preparation ID, not transaction bytes, signatures, signer methods or session identifiers. Restoration says `signingStatus: unknown`; expiry, wallet rejection, cancellation or reload never releases the slot or proves non-signing. `readCosmosSigningSlot` distinguishes both phases, while the signed-only reader rejects a reserved slot instead of reporting it empty. Only genuine signed evidence matching the reserved preparation ID, account number, unsigned/sign-document/intent hashes and observation time may replace it with `signed-observed`. Failed or uncertain transition writes retain whichever blocking phase reached storage. Standalone imports of already-signed evidence remain observation-only and cannot authorize another signature.

This API is for an explicit signing workflow, not automatic reservation on every quote edit. The transport below is connected to the separate signing review UI described below. Reservation reconciliation/release and the submission pipeline remain unfinished. Native-browser QA additionally verifies that expired and consumed synthetic reservations remain blocking after reload; synthetic integration tests cover real preparation/evidence identities, concurrent acquisition, selector mutation, account invalidation, expiry, conflicting observations and persistence failures.

### Reserved Cosmos DIRECT signing transport

`src/swap/cosmos-injected-direct-signing.ts` implements a one-shot signature request for the exact original injected provider. It requires a genuine preparation/source-bound verification, a current bound account, an exact confirmation action/preparation ID/transaction hash, and the previously persisted reservation. Confirmation is an application-call contract, not proof of a human gesture: the UI below supplies it only after review, acknowledgement and a separate explicit request. There is no automatic connection, signing fallback, Amino conversion, chain suggestion or broadcast. Hardware-backed bindings fail closed until their signing paths are reviewed.

Before invoking `signDirect`, the reservation transitions under the native slot lock to `signing-requested` with exact readback. Rejection, cancellation, timeout, invalid response and reload never reset it. Account/source/expiry, provider-method identity and the consumed record are checked immediately before invocation. A page-local pending-provider guard remains held until raw validation/signing settles even when local observation times out or is cancelled; late responses are discarded. The requested state means outcome unknown, not that signing succeeded.

The provider receives copies of the reviewed body/auth bytes and exact chain/account, with fee/memo preservation requested and balance checks not disabled. Responses must preserve all signed content and include the expected public key; the existing source-bound low-S signature verifier runs again before a signed observation is persisted. The complete uint64 account number is sent as a decimal string; returned integer/string/bigint or primitive Long words are checked without invoking a response object's `toString`. Negative, lossy, malformed and getter-backed values are rejected. The provider's documented ability to modify returned sign documents is therefore never accepted silently. References: [Keplr signing API](https://docs.keplr.app/api/guide/sign-a-message), [Keplr CosmJS integration](https://docs.keplr.app/api/use-with/cosmjs), and [official provider distribution](https://cdn.jsdelivr.net/npm/@keplr-wallet/provider/build/core.js), inspected 2026-09-02.

Only a successful current response returns verified signed TxRaw bytes to the caller's memory for a later separately authorized submission. Persistent history and evidence objects still contain no transaction bytes; errors, cancelled/expired results and late responses expose none. Nothing submits those bytes here. Synthetic tests exercise genuine provider identity, exact once-only invocation, altered responses, malformed signatures, uint64 precision, unavailable methods, storage failures, cancellation, timeout, account changes and expiry. No real wallet has been asked to sign, and this does not establish real-extension/hardware compatibility or mainnet readiness.

### Cosmos signing review UI

After source-bound Cosmos route/intent simulation succeeds, Universe Routes presents its own optional testnet account connection. The connection panel provides its exact genuine connection/binding/provider to `CosmosSigningReviewPanel` only after explicit account selection; it disposes that context on forgetting, invalidation or leaving the view. The Wallets tab remains connection-only, and selections are not silently transferred across views.

Preparing a review performs account/evidence checks and reads existing signing history, without reserving or signing. The card shows full network/account/recipient/venue identity; exact integer base-unit send, estimated receive, minimum receive, fee and total debit; expiry; and expandable sequence/gas/timeout/hashes. Unknown decimals/symbols are not invented. Different fee/source denoms remain separate, while same-denom totals use BigInt addition. Simulation is not presented as certification or a guarantee.

An unchecked acknowledgement plus a separate `Request swap signature — no broadcast` action is required. The action reserves and freshly rechecks the exact reviewed preparation before invoking the one-shot transport. Synchronous busy guards prevent double clicks. Account/intent/source/route/provider changes clear the review, unchecked acknowledgement and in-memory signed data, abort local observation and ignore late results. Expired, unsupported-hardware, occupied or unreadable-history states block signing. Cancellation is explicitly local-only and never releases reservations. The signed receipt says not submitted, has no broadcast button, and keeps signed bytes only in a non-rendered page-memory ref until the view changes/closes. No reservation recovery/release or submission UI is available yet.

UI tests cover explicit actions, exact confirmation and units, duplicates, stale context, expiry, blocked history, cancellation and late results. `scripts/qaCosmosSigningReview.mjs` runs a separate Vite server with UI-only stubs and a clearly labelled synthetic fixture; the stubs never modify production modules. It checks desktop/tablet/375px/320px/200% text, long denoms/hashes, keyboard acknowledgement/focus, local cancellation and expiry. This visual harness is not evidence of live wallet signing; genuine signing/evidence/storage behavior is tested separately in the Cosmos source integration suite. Claude's hierarchy recommendation was used, but its suggested natural reservation expiry was rejected because the durable reservation deliberately does not auto-release.

### Cosmos signed-but-not-submitted evidence boundary

`src/swap/cosmos-injected-signed-swap-evidence.ts` accepts already-signed TxRaw bytes only alongside a genuine current connection, account binding, signing preparation and source-bound Osmosis verification. It snapshots caller-owned inputs before awaiting, matches the exact preparation/session/provenance, and shares the cryptographic verification function with the existing post-submission recovery code. This verifies one compact low-S secp256k1 signature over the exact DIRECT sign document, unchanged body/auth bytes, authority public key, transaction hash and canonical intent hash. The signature check itself neither creates a submitted record nor touches storage.

The result is a frozen, identity-branded `signed-not-submitted` receipt with hashes, reviewed amounts and provenance, not signed or unsigned transaction bytes. It grants no signing, submission, broadcast, execution or automatic resend authority. Wallet/source validity and the live clock are rechecked after asynchronous verification. Synthetic tests cover malformed/high-S/wrong-key signatures, changed bytes, clones, substituted sessions, expiry during the final account read, source mutation and keystore events. No real wallet was connected or asked to sign. Under the critical-action safety model this is verification-only; the later R3 submission step still requires separate explicit authorization, durable duplicate prevention and reconciliation. A valid signature is never evidence of network submission or finality.

### Solana pre-signing preparation boundary

`src/swap/solana-standard-signing-preparation.ts` joins the exact current Wallet Standard account binding to a genuine in-memory source-bound SPL Token Swap verification. Structural copies are not capabilities: connection objects and source-bound verification results are branded inside their creating modules, and mutation after verification invalidates the capability. The selected address must be the unsigned transaction fee payer/authority, its exact CAIP chain must match, and only transaction version 0 is accepted because the installed decoder supports unsigned v0 transactions only.

Preparation recomputes the unsigned transaction and canonical intent hashes, checks the source-bound quote amounts and slippage, and revalidates both capabilities after asynchronous hashing. Its frozen page-local result contains the wallet/account/session identity, chain, venue, execution target, mints, destination token account and owner, exact input/quoted/minimum output, simulated network fee, expiry, transaction bytes and source-policy fingerprints needed for a future signing review. The lifetime is the earlier of the account binding and quote expiry.

This package deliberately has no wallet method, signer, RPC reader, storage writer, or broadcaster. `signingEnabled`, `submissionEnabled`, and `executionEnabled` remain false and `requiresFreshVerification` remains true. It is neither signature permission nor reusable recovery authority. A future explicitly authorized signing step must show this summary, freshly verify blockhash and quote evidence at its own commit boundary, constrain the exact Wallet Standard call, validate returned signed bytes through `solana-swap-recovery.ts`, establish durable no-resend recovery state, and only then consider a separately authorized submission.

### Solana signed-but-not-submitted evidence boundary

`src/swap/solana-standard-signed-swap-evidence.ts` separates a wallet-returned signature from transaction submission. It accepts only the genuine current account binding, genuine preparation object, and genuine source-bound SPL verification created in the same page lifetime. Before and after cryptographic work it rechecks the account/session capabilities, preparation expiry, exact unsigned transaction, amount/fee/destination summary, source/route/manifest/read-policy fingerprints, and all disabled authority flags.

The shared verifier in `solana-swap-recovery.ts` then requires exactly one Ed25519 signature by the prepared authority, a byte-identical unsigned message body, matching base58 signature, transaction and canonical-intent SHA-256 values, recent blockhash, and last-valid block height. A structural copy, changed message, different signer, expired preparation, provider event, or silent account mutation fails closed.

Success is explicitly `signed-not-submitted`, not `submitted`. The frozen evidence keeps the public signature, hashes, prepared summary, and provenance but deliberately omits the signed transaction bytes, so restoring or passing the evidence cannot rebroadcast it. `signedTransactionBytesStored` and both execution flags remain false, `automaticResendBlocked` is true, and a separately reviewed transport plus explicit submission authorization is still required. This boundary never reads a wallet signing method, calls RPC, writes storage, or broadcasts.

### Asset registry

Asset identity is keyed by CAIP-19, never by symbol or display name. Metadata may come from a built-in review, a signed list, a current on-chain read, or a user import. A token list is metadata, not a security approval: even schema-valid lists may be malicious or stale. Uniswap’s Token Lists specification similarly describes metadata lists and explicitly notes that list versioning is not security protection. Source: [Token Lists specification](https://github.com/Uniswap/token-lists) (reviewed 2026-09-01).

Imported RealDEX asset manifests are inspection-only. They cannot set `execution` to `ready`, install code, select a spender, add liquidity, or request a wallet signature.

Signed asset manifests add publisher authentication without conflating it with token safety. The user first session-pins an exact source descriptor containing the source ID, EIP-191 signer address, allowed CAIP-2 chains, and HTTPS policy evidence. RealDEX fingerprints that descriptor, verifies the manifest's canonical payload and expiry, and persists the highest accepted revision and payload hash per fingerprint. Older revisions and different payloads reusing the same revision are rejected. An exact replay is harmless and remains inspection-only. The v1 signing domain and `LOCALSWAP_ASSET_SOURCE_PRIVATE_KEY` environment-variable name remain as compatibility identifiers; they are not the product display name and must not be changed without an explicit manifest-version migration.

Every signed asset must still have `provenance: signed-list` and `execution: design-gate`. Exact CAIP-19 metadata conflicts are shown as critical findings and cannot replace built-in records; matching symbols on different asset IDs are shown as collision warnings. For EVM ERC-20 entries on the configured RPC chain, the UI additionally requires contract bytecode and reads the current `symbol`, `name`, and `decimals`.

Optional read-only non-EVM verification requires two public HTTPS endpoints on distinct hosts for each configured family and keeps their URLs in page state. A single endpoint, two paths on one host, one unavailable reader, or disagreeing observations cannot produce a successful result. Each request omits browser credentials and referrer data, has an eight-second timeout, and stops reading after one megabyte. Changing a source or endpoint advances an attempt ID, clears prior results, and prevents a late response from updating the accepted manifest or revision head.

For each independent Solana reader, SPL verification binds the CAIP-2 genesis-hash prefix to `getGenesisHash`, then checks a parsed mint account's owner program, initialized state, and decimals. Both readers must agree, and the aggregate deliberately reports `partial`, not `verified`, because the core SPL mint state does not establish the signed symbol or name; Solana documents token metadata separately from mint basics. For each Cosmos reader, verification binds the node-reported chain ID and requires exact current `x/bank` metadata for base denom, display unit exponent, symbol, and name; both readers must agree before the aggregate becomes `verified`. Offline readers, wrong chains, unsupported asset types, malformed responses, and metadata mismatches never become verified. Sources: [Solana getGenesisHash](https://solana.com/docs/rpc/http/getgenesishash), [Solana SPL Token basics](https://solana.com/docs/tokens/basics), [Cosmos SDK x/bank](https://docs.cosmos.network/sdk/v0.50/build/modules/bank/README), [Cosmos SDK bank query routes](https://github.com/cosmos/cosmos-sdk/blob/main/proto/cosmos/bank/v1beta1/query.proto) (reviewed 2026-09-01).

Even a matching on-chain read does not install a swap adapter or enable execution.

Publishers can produce the exact canonical signature without exposing the key in a file or command argument:

```powershell
$env:LOCALSWAP_ASSET_SOURCE_PRIVATE_KEY = "<enter securely for this shell>"
npm run sign:asset-manifest -- docs/asset-source.example.json docs/signed-asset-manifest.unsigned.example.json signed-output.json
Remove-Item Env:LOCALSWAP_ASSET_SOURCE_PRIVATE_KEY
```

The example signer address and evidence URLs are placeholders and must be replaced. The signing command refuses to overwrite an existing output file and never prints the private key.

### Venue and route adapters

An executable swap or bridge requires installed code for an exact venue or route. Each adapter must provide:

- supported chain and asset identities;
- wallet methods and address validation;
- quote origin, expiry, decimals, rounding, minimum received, fees, and total debit;
- simulation and balance requirements;
- approval/permit scope and spender identity;
- transaction construction and duplicate protection;
- included, confirmed, finalized, delayed, replaced, dropped, reverted, and unknown handling;
- receipt, explorer, recovery, refund, acknowledgement, or support evidence.

### Deterministic EVM venue discovery

`src/swap/evm-venue-discovery.ts` accepts up to 32 locally configured RealDEX v1 factories (`LocalSwapFactory` artifacts) on one exact EVM chain. It does not trust an address because it responds to the expected ABI. The deployed factory runtime bytecode must hash to the value pinned in `src/swap/local-amm-code-identities.json`; a Solidity test recomputes that hash from the current compiler artifact so contract changes cannot silently leave the frontend allowlist stale.

For each matching factory, discovery reads the exact pair from `getPool`, requires pool bytecode, checks the pool's immutable `factory()` origin, and verifies both token addresses. Zero pools, duplicate factories, duplicate pool targets, wrong chains, changed factory bytecode, spoofed origins, and wrong pairs remain rejection diagnostics and never become executable route descriptors. A manually entered pool is not sufficient for Swap or Liquidity readiness; Setup must re-establish the factory and pool proof after configuration changes.

All verified direct pools become separate route descriptors and are quoted through the same EVM adapter. The common engine ranks only quotes for the same destination CAIP-19 asset by minimum received. The UI stores the selected descriptor alongside the displayed quote, and execution revalidates that route fingerprint, exact pool target, method, account, session revision, amount, slippage, approval, and expiry. Per-pool price impact is computed from that pool's current reserves and quote instead of the Setup screen's primary-pool reserves.

### Atomic RealDEX multi-hop

`LocalSwapRouter` is a stateless, adminless execution target for simple paths of two through four pools. Its runtime hash is pinned beside the factory hash and checked from the compiler artifact. Discovery never accepts arbitrary router calldata: it builds edges only from pools that already passed factory runtime, origin, bytecode, and pair verification, then enumerates simple paths with no repeated pool or token.

The route descriptor binds the exact router while adapter data binds the ordered pools and tokens. Quote and execution re-check router bytecode and every ordered pair; execution checks again after any approval and before the swap submission. The user approves only the exact input amount to the router. Intermediate outputs remain in the router only within one transaction, and final minimum-output failure reverts the complete path. Transfer-delta and consumed-allowance checks reject unsupported token behavior rather than leaving partial intermediate state.

### Common route quote engine

For bridge execution, recovery reservation preparation is a synchronous pre-adapter hook inside the execution critical section. It runs after account revalidation and exact persistent-guard readback, but before adapter code. Connection refusal, account/network mismatch, duplicate detection, and guard persistence failure never reach the hook. A hook failure prevents adapter invocation and attempts an exact guard removal; inability to prove removal keeps the guard. The reservation journal also rejects quote/execution counterpart collisions before writing, so a failed admission cannot corrupt otherwise valid recovery history.

`src/routing/` now defines a shared quote boundary for swap and bridge adapters. The initial registry contains the six exact CCTP and IBC directions already present in the app. Each descriptor binds source and destination CAIP-19 identities, wallet capability, adapter revision, maximum quote lifetime, trust boundary, finality coverage, and evidence.

The engine rejects a candidate unless the exact adapter is installed and declares support. A returned quote is then bound to the route fingerprint and to the request's account, recipient, wallet capability, wallet-session revision, asset IDs, amount, and slippage. It also validates expiry, minimum received, fee identities, approval scope, and transaction preview before ranking comparable quotes. Quotes are ranked only when they share the exact requested destination asset; fee assets remain visible instead of being silently converted using an unverified price.

Every current financial binding is a domain-separated Keccak-256 digest over a canonical typed encoding. Route descriptors include every execution, evidence, trust, finality, asset, adapter, and revision field; v3 quote requests include a cryptographically random execution-intent ID plus the exact wallet-grant fingerprint and all account, recipient, session, amount, and slippage fields. Wallet grants canonicalize scope ordering while preserving value and array-type distinctions. Legacy bridge descriptors and new EVM recovery identities use separate domains, so a digest from one authority class cannot be replayed as another. Historical 32-bit FNV values are retained solely for exact read-only finality/recovery compatibility and are rejected by all current quote, execution, and recovery-append paths.

`src/routing/execution-intent.ts` creates canonical UUIDv4-shaped IDs from browser cryptographic randomness. Swap and Bridge retain one ID while re-quoting the same human action; changing amount, slippage, token direction, route/family, destination recipient, venue configuration, or wallet authority creates a new intent before another quote can become executable. Both screens disclose a shortened non-secret intent ID beside the quote so the confirmation and later evidence can be correlated.

`src/routing/cross-tab-execution-lock.ts` hashes that route/intent guard into one bounded Web Locks name. The engine requests an origin-wide exclusive lock with `ifAvailable` before it calls `connectAccount`; a second tab fails immediately instead of queuing a later wallet request. Account revalidation, the legacy/current persistent checks, durable write/readback, adapter execution, receipt validation, and any explicit-failure unlock all occur within the same critical section. A browser without a functioning Web Locks service cannot execute routes because localStorage alone has no atomic compare-and-set across tabs.

Inside the origin lock, `src/routing/execution-guard.ts` writes a strict v3 record under the exact route/intent key and requires byte-identical storage readback. Quote ID, request fingerprint, and creation time remain inside the record for audit, but quote or grant refresh cannot change the lock key. The record deliberately has no expiry: wall-clock time, quote expiry, missing storage evidence, or an unavailable provider cannot prove that an unknown value transfer did not execute. Opaque v2/FNV route guards, legacy expiring records, and malformed values remain blocking at route scope. A `failed` receipt clears the current intent key only with one of three exact proofs: no value-transfer submission (with any approval transaction already terminal), an exact status-zero EVM swap receipt without a changed replacement, or an exact Cosmos source transaction with a non-zero result code. An adapter/provider error, a bare transaction hash, or any other ambiguous outcome retains the guard. If browser persistence is unavailable, the engine fails before calling the adapter rather than relying on a button state or an in-memory lock that disappears on reload.

The installed EVM local AMM, CCTP, and IBC implementations now implement the shared quote and execution interface. The Swap and Bridge screens connect the exact source account, build one common request, obtain a provider-backed estimate through `quoteRoutes`, display the normalized values, and submit that same bound quote through `executeRouteQuote`. Provider-specific state is kept as adapter data and revalidated by its owning adapter before submission.

The EVM local AMM adapter constructs an exact dynamic CAIP route for the selected chain, pool, and token pair. Its quote reads the pool output and current allowance, exposes an exact approval when needed, marks wallet gas as unpriced rather than inventing a fee, and binds the pool target, `swapExactIn` method, deadline, account, session revision, amount, slippage, and token identities. Approval and swap use this same quote. A rejection, expiry, account change, network change, pool-pair change, or target mismatch stops before value movement can continue.

`src/swap/evm-swap-recovery.ts` persists a bounded, revisioned recovery journal only after an EVM approval or swap transaction hash exists. New v3 records require the full submitted transaction envelope and bind the exact Keccak-256 route and request fingerprints, quote, chain, account, recipient, CAIP-19 assets, input and minimum-output base units, execution target and method, provider, plus the submitted transaction's `from`, `to`, nonce, calldata, value, chain ID, and block observed immediately before submission. Existing v1/v2 FNV records remain readable for tracking but cannot accept a new receipt, transaction, or authority. Reloading restores the latest validated record without restoring quote authority. A manual refresh reads only the configured RPC and scans at most 24 blocks per invocation when the original hash is absent and its account nonce has been consumed; the next block cursor is persisted for bounded continuation. An exact envelope match is classified as fee-only repricing and may inherit its receipt, while a self-cancellation or any changed envelope becomes a terminal replaced state and is never swap success. A wrong chain, malformed transaction or receipt, stale revision, stage regression, or disappearance of previously observed evidence retains the prior record and never authorizes a retry. Missing or provider-pruned evidence remains submitted/searching/unknown and retains the duplicate guard rather than being interpreted as dropped or safe to resend.

The injected-wallet session is an explicit reducer state rather than a collection of independent booleans. `src/wallet/eip6963.ts` listens for the standard `eip6963:announceProvider` event, requests announcements after installing the listener, and keeps legacy `window.ethereum` only as a fallback. A single provider may become the default candidate; two or more providers without a persisted exact UUID require an explicit selection. Conflicting announcements for the same UUID are quarantined instead of selecting either provider. Names, icons, and reverse-DNS values remain self-asserted display metadata, not trust evidence.

The selected provider object is injected consistently into Swap, Liquidity, and EVM-source CCTP estimation/execution. Provider selection, account, chain, and disconnect changes advance a monotonic session revision and invalidate active quotes. Active quotes are also invalidated at their exact expiry; execution independently checks the revision and current wallet identity, so UI timing cannot bypass the gate. No account request occurs during discovery or selection—connection remains a separate user action.

`src/wallet/capabilities.ts` adds a transport-neutral execution grant. A local injected provider binding explicitly does not claim that CAIP-25 negotiation occurred; it records the adapter-observed transport identity and the minimum method/notification contract used by that adapter. A real CAIP-25 response is accepted only as an exact chain-specific scope with CAIP-10 accounts, bounded arrays, known fields, a short expiry, and a monotonic revision. The normalized grant is fingerprinted into every route request, then rechecked during both quote validation and execution. Wrong chain, account, method, notification set, transport, revision, or expiry fails closed. CAIP-25 parsing alone does not install mobile-link, or hardware transport code.

WalletConnect and Reown are not part of RealDEX: their community licence is incompatible with AGPL-3.0, so only injected providers (EIP-1193 / EIP-6963), Wallet Standard, and Keplr-compatible signers are supported.

`src/wallet/bitcoin-psbt.ts` is the first Bitcoin transaction boundary, still disconnected from signing. It accepts canonical base64 PSBT v0 only, parses minimally encoded and duplicate-free global/input/output maps, requires the BIP-174 unsigned transaction in legacy serialization with empty scriptSigs, and bounds file/map/count/script sizes. Each input must carry exactly one witness UTXO and match an exact declared txid, vout, sequence, amount, and native P2WPKH or P2TR script. Outputs must be metadata-free and match an ordered recipient/change list; their sum plus the exact visible fee must equal the input sum. Transaction version, locktime, canonical timestamps, and a maximum 15-minute lifetime are also bound. Any partial/final signature, unsafe sighash, non-witness input, unknown/proprietary field, PSBT v2 marker, extra output, altered UTXO, or trailing byte rejects the document. BIP-174 requires version 0 to include one unsigned transaction and defines witness UTXO/signature/finalization fields; BIP-370 moves version 2 transaction data into separate fields, so this first parser rejects rather than partially interpreting it. Sources: [BIP-174](https://github.com/bitcoin/bips/blob/master/bip-0174.mediawiki), [BIP-370](https://github.com/bitcoin/bips/blob/master/bip-0370.mediawiki), and [BIP-141](https://github.com/bitcoin/bips/blob/master/bip-0141.mediawiki) (reviewed 2026-09-01).

The PSBT report contains only counts, amounts, fee, expiry, and cryptographic fingerprints and always sets execution, signing, and broadcast to false. `src/wallet/bitcoin-utxo-quorum.ts` can then re-inspect that exact unexpired intent and query exactly two distinct public HTTPS Esplora hosts. BIP122 chain identity is checked from the first 32 hexadecimal characters of each host's height-zero block hash. Both observations must bind every input's exact txid/vout internally, witness value, scriptPubKey, confirmed block height/hash, unspent state, minimum confirmation count, and a bounded tip-height divergence. Only GET is allowed; endpoint credentials, query/fragment state, local/private hosts, duplicate hosts, malformed or oversized responses, timeouts, and any disagreement fail closed. The returned UI report omits raw txids, addresses, and scripts and endpoint/PSBT changes revoke late async results. Esplora's documented POST broadcast endpoint is never called. Sources: Blockstream's [Esplora HTTP API](https://github.com/Blockstream/esplora/blob/master/API.md) and Chain Agnostic's [BIP122 chain profile](https://namespaces.chainagnostic.org/bip122/caip2) (reviewed 2026-09-01).

Two public indexers can still share operators, upstream nodes, censorship, surveillance, or incorrect data. The quorum proves corroborated read evidence, not key ownership, fee reasonableness, liquidity, price, Bitcoin consensus, or atomic swap semantics. A bundled trusted endpoint policy, PSBT v2, legacy/P2SH/P2WSH input proof, Taproot script paths, Bitcoin swap semantics, atomicity, signing, finalization, broadcast, and recovery remain separate future gates.

`bitcoin-psbt.ts` now also derives a conservative signed-size range without creating signatures. The stripped unsigned transaction contributes four weight units per byte; the SegWit marker/flag and supported P2WPKH or P2TR key-path witness serialization bounds are added, then BIP-141 weight is rounded up to vbytes. Integer milli-sat/vB bounds avoid floating-point authority. `bitcoin-fee-policy.ts` rebinds the fresh PSBT inspection and the exact successful UTXO quorum before requesting Esplora's documented six-block `/fee-estimates` value from both readers. The two estimates must differ by no more than 50%; the actual lower fee-rate bound must be at least 1 sat/vB and half the higher recommendation, while its upper bound must be at most 1000 sat/vB and five times the lower recommendation. Every threshold is returned as an explicit design-gate policy, and success still cannot sign or broadcast. Fee forecasts are advisory and neither prove mempool acceptance nor guarantee confirmation. A user-owned, signed, network-specific production policy remains future work.

`bitcoin-read-policy.ts` supplies that signed policy container without bundling or trusting a production publisher. A local source pin fixes an EIP-191 signer, allowed BIP122 chain references, and evidence. The canonical signed payload fixes the source fingerprint, one exact chain, two independent normalized public HTTPS Esplora bases, every UTXO and fee threshold, evidence, issue/expiry timestamps, and a monotonic revision. A local current head stores only revision and payload hash per source fingerprint and blocks rollback or same-revision equivocation. The policy and its signature are revalidated immediately before creating readers, including expiry and PSBT chain equality. This turns the prior built-in fee policy into a test/default component rather than sufficient read authority. EIP-191 provides domain-separated signed-data framing; publisher-key governance and real operator independence still require human review. No policy grants wallet, signing, finalization, broadcast, or swap authority.

`bitcoin-signed-psbt.ts` adds the next offline boundary without installing a wallet transport. A wallet-returned envelope lasts at most five minutes and names the exact original PSBT fingerprint. The verifier freshly re-inspects the original intent, revalidates the signed read policy, and requires exact bindings to the UTXO and fee reports before parsing the returned PSBT. Its unsigned transaction and all non-signature global/input/output map entries must remain byte-identical. Native P2WPKH uses the BIP-143 digest and accepts exactly one strict low-S DER ECDSA `SIGHASH_ALL` signature from a compressed key whose HASH160 matches the witness program. Native P2TR key path uses the BIP-341 `TapSighash` message and BIP-340 verification, accepting only canonical default or all-output hash modes. Final scripts, script-path fields, unknown metadata, substitution, and partial input coverage fail closed. The result retains only fingerprints and counts and has execution, signing, finalization, and broadcast explicitly disabled. Sources: [BIP-174](https://github.com/bitcoin/bips/blob/master/bip-0174.mediawiki), [BIP-143](https://github.com/bitcoin/bips/blob/master/bip-0143.mediawiki), [BIP-340](https://github.com/bitcoin/bips/blob/master/bip-0340.mediawiki), and [BIP-341](https://github.com/bitcoin/bips/blob/master/bip-0341.mediawiki) (reviewed 2026-09-01).

`bitcoin-finalized-psbt.ts` verifies an externally finalized PSBT but deliberately implements neither a Finalizer nor a broadcast-capable Transaction Extractor. It freshly replays the signed-PSBT gate, requires exact signed-result fingerprint binding, and accepts per input only the unchanged witness UTXO and one final scriptWitness. Native P2WPKH must contain exactly the verified DER signature and compressed public key; native P2TR must contain only the verified key-path signature. `finalScriptSig`, retained partial signatures/derivation/sighash metadata, extra or reordered stack items, non-minimal CompactSize, altered transaction maps, and stale evidence fail closed. Once every input matches, the verifier reconstructs traditional and witness serializations in memory to derive txid, wtxid, BIP-141 weight/vsize, and exact fee rate, but returns no transaction bytes and keeps extraction and broadcast false. BIP-174 defines the Finalizer and Extractor roles and requires UTXO retention; BIP-141 defines the two identifiers and witness serialization. Sources: [BIP-174](https://github.com/bitcoin/bips/blob/master/bip-0174.mediawiki) and [BIP-141](https://github.com/bitcoin/bips/blob/master/bip-0141.mediawiki) (reviewed 2026-09-01).

The execution target and method are part of the reviewed route descriptor and route fingerprint; an adapter cannot redirect a valid-looking quote to a different contract, program, channel, or method. The active wallet account is checked before quote creation, after provider estimation, and immediately before the duplicate guard and value-moving adapter call. Adapter progress receipts are structurally validated before they reach UI state, must remain `pending`, and must keep one provider identity through the final receipt. A pending, unknown, or ambiguously failed execution keeps both an in-memory and local browser guard; only the exact failure proofs above clear it automatically.

Bridge receipts additionally require a recoverable, protocol-specific finality identity before they may claim `pending` or `confirmed`. The common record binds schema, route fingerprint, quote ID, execution ID, provider, protocol cursor, evidence, revision, and timestamps. Its monotonic stages are `source-submitted → source-included → awaiting-proof → destination-submitted → destination-confirmed`, with terminal or side states for `failed`, `refundable`, and `unknown`. Current storage uses a domain-separated Keccak operation key over the route, execution, and quote instead of one mutable route slot. Up to 16 distinct records or pre-execution reservations remain independently accounted; execution/quote identity collisions, stale revisions, illegal transitions, cursor or provider mutation, and removal or mutation of existing evidence are rejected. The quote-bound reservation is synchronously persisted before the adapter is entered. For CCTP, Bridge Kit's typed successful `burn` event is validated and converted immediately to a source-submitted record, before its longer attestation/forwarding operation resolves; only the burn step contributes source candidates. For IBC, the exact packet identity is emitted directly after the successful source response is parsed. A later provider result reconciles into the existing record rather than replacing revision one. A leftover reservation means submission is unresolved and is shown as such after reload. Exact legacy records may be loaded for tracking but cannot be extended. A second domain-separated, route-scoped Web Lock wraps reservation, execution, and first evidence save; refresh acquires the same lock and reloads the durable latest operation before observing and saving. This ordering prevents last-slot admission races, post-submission evidence gaps during provider polling, and same-revision lost updates across tabs. Lock absence, service failure, or contention does not fall back to a localStorage check. A reducer operation ID rejects late refresh results, and persisted records load only for the exact current route fingerprint. Initial and updated records advance UI recovery state only after byte-identical local-storage readback; capacity, quota, permission, mutation, or readback failure is reported while the prior durable state remains authoritative.

CCTP V2 refresh queries Circle's message service with the reviewed source domain and recorded transaction candidates. A new cursor binds the exact source burn token, base-unit amount, source message sender, and destination mint recipient. RealDEX locally parses the raw CCTP message header and BurnMessageV2 body, requires those values and both domains to match, and rejects malformed or ambiguous messages instead of trusting the decoded JSON projection. Historical cursors without this transfer binding are tracking-only and cannot refresh. For Base Sepolia and Arbitrum Sepolia sources, two independent public RPC readers must additionally agree on the source chain, close-enough heads, exact successful receipt, block identity, and normalized logs. One canonical MessageTransmitterV2 `MessageSent(bytes)` log must equal Circle's message and reach two confirmations before `source-included`; later stages cannot persist without that source-tx/source-log pair. Bridge Kit `success` alone therefore remains `source-submitted`, and a complete attestation remains awaiting proof. A Forwarding Service destination hash advances only to destination submitted unless the destination is Base Sepolia or Arbitrum Sepolia and two destination RPC readers agree on a successful two-confirmation receipt containing the exact raw-message `MessageReceived` and net `MintAndWithdraw` events. Only then can an EVM destination reach destination confirmed. Solana-side program/account proof remains absent. IBC refresh first reconstructs the exact `send_packet` identity from the source transaction, verifies the reviewed channel pair, and then reads the corresponding destination acknowledgement. All of these bridge reads, including both pre-sign channel checks, use credential-free requests with an eight-second timeout, one-megabyte response cap, strict JSON parsing, no referrer, and no cache reuse. Timeout, oversize, malformed content, or transport failure exits the refresh while preserving the durable-latest evidence. REST-reported success and application error both advance only to non-terminal `destination-observed`, with the outcome and proof height retained in evidence. The configured REST response is not independently proof-verified against a trusted IBC header, so neither outcome can become confirmed, failed, refundable, or retry authority. Contradictory outcomes for one acknowledgement identity/proof height and legacy terminal claims carrying REST acknowledgement evidence are rejected. Absence before or after timeout also remains non-terminal and cannot authorize a retry or refund.

All Base-dependent CCTP execution remains paused as of 2026-09-02. Both pinned Base Sepolia readers first returned empty code and later again returned the documented USDC proxy. A dedicated read-only evidence boundary now requires both hosts to agree on chain/head, proxy code, Circle proxy implementation slot, implementation code, and strict ERC-20 metadata, but its result fixes execution to false and release approval required. The universal asset registry marks Base Sepolia USDC `design-gate` rather than ready. Re-enabling requires independent source/bytecode review, any required route-binding revision, and an explicit release decision; historical recovery remains readable.

An assessment-only signed release manifest binds a separately pinned EIP-191 reviewer, that fresh observation fingerprint, code identities, official Circle source revision/build settings and verification-artifact hashes, monotonic revision, and expiry. It rejects source or signer substitution, evidence changes, rollback, revision conflicts, and authority-flag mutation. A valid manifest still cannot enable signing, submission, or execution; no production reviewer trust root is installed.

## Non-negotiable invariants

1. Discovery does not enable execution.
2. A matching symbol does not establish asset identity or bridge equivalence.
3. Wallet connection does not authorize approval, signing, or value movement.
4. A quote is bound to the account, chain, asset IDs, venue/route revision, amount, recipient, fees, and expiry.
5. Account, chain, capability, route, balance, allowance, or quote changes invalidate confirmation.
6. Duplicate prevention is structural; a disabled button is not sufficient.
7. Submitted or source-included is not destination or product completion.
8. Unknown state is preserved until evidence resolves it.
9. Mainnet and real-asset routes require an independent release gate and security review.

## External EVM V2 safety boundary

`src/swap/external-evm-v2.ts` implements the first external-AMM boundary without enabling a public venue. It models token-to-token exact-input paths of one to three V2 pairs and accepts only the 0.30% constant-product fee model used by the official Uniswap V2 library. The official Router02 source exposes `factory()`, calculates `getAmountsOut`, and executes `swapExactTokensForTokens(amountIn, amountOutMin, path, to, deadline)`. The official Pair exposes `factory`, `token0`, `token1`, and `getReserves`. Sources: [Uniswap V2 Router02](https://github.com/Uniswap/v2-periphery/blob/master/contracts/UniswapV2Router02.sol), [Uniswap V2 library](https://github.com/Uniswap/v2-periphery/blob/master/contracts/libraries/UniswapV2Library.sol), and [Uniswap V2 Pair](https://github.com/Uniswap/v2-core/blob/master/contracts/UniswapV2Pair.sol) (retrieved 2026-09-01).

`src/swap/external-evm-v2-read-policy.ts` extends that boundary from venue identity into quote integrity. A strict JSON intent fixes the exact venue and chain, canonical uint256 base-unit input, non-zero recipient, 0–500 bps slippage, canonical issue time, and at-most-five-minute expiry; the generated transaction deadline is capped by that expiry. The verifier recreates both readers exclusively from the independently signed policy, re-verifies the signed venue and live contract graph, and has each reader independently fetch reserves, reproduce every 0.30% constant-product hop, and compare the result with its Router. The two independently valid quotes must then be byte-for-byte equivalent in amount path, minimum output, recipient, deadline, quote ID, and calldata. Manifest, policy, intent expiry, and deadline are revalidated after the quorum completes, preventing an in-flight expiry from becoming a successful preview. A stale or divergent snapshot stops without averaging, selecting one endpoint, requesting a signature, or exposing submission. The non-executing preflight now accepts only an unmodified, unexpired policy-bound report, repeats the same signed-artifact and two-reader checks, and returns a revalidation receipt only if every bound quote and observation field remains identical; otherwise it requires a new explicit review. Universe displays that read-only result, automatically removes green evidence at the earliest quote, venue-manifest, or read-policy expiry, and invalidates it whenever an upstream input changes. A future execution adapter must consume this exact revalidated quote; the current report deliberately keeps execution, signing, and submission disabled.

Before quoting, RealDEX requires the exact chain and runtime hashes for the Router, Factory, and every Pair; Router-to-Factory identity; Factory `getPair` identity; each Pair's immutable origin and ordered tokens; a simple non-cyclic path; and at least two HTTPS evidence URLs. It then reads every reserve, independently recomputes all hop outputs with the 997/1000 formula, and requires the Router's `getAmountsOut` array to match exactly. The generated calldata is decoded again and bound to the verified path, exact input, minimum output, recipient, and five-minute deadline. Immediately before a future execution transport may use it, code and origin identities must be reverified and the deadline and calldata rebound.

`src/swap/external-evm-v2-source.ts` supplies provenance and live quorum without bundling a venue. A JSON-safe manifest serializes chain IDs as canonical decimal strings and is signed with EIP-191 only after binding the exact source-descriptor fingerprint, source ID, revision, issue/expiry timestamps, all venue identities, and evidence. The validity window is capped at 30 days. A source substitution, signer mismatch, chain-scope violation, unknown field, duplicate venue or fingerprint, rollback, or same-revision equivocation is rejected. Universe stores only the last accepted revision and payload hash for that exact source fingerprint; it does not store signing or execution authority.

`src/swap/external-evm-v2-read-policy.ts` removes arbitrary RPC text and caller-created readers from the source-bound venue path. A separately pinned EIP-191 reviewer signs one canonical policy containing the exact EIP-155 chain, two normalized public HTTPS endpoints on different hostnames, the installed verification-boundary ID, at-most-30-day validity, monotonic revision, and evidence. Immediately before the live check, the entrypoint freshly revalidates both the venue manifest and policy, selects the venue only from the signed manifest, requires the reviewer address to differ from the venue publisher, requires the chain bindings to match, and creates readers only from the signed endpoint pair. Universe stores only each source-specific revision/payload-hash head, displays policy endpoints read-only, and invalidates prior results on policy changes. Two hostnames do not prove separate operators or upstream infrastructure, and successful identity verification grants no signing or execution authority.

After signature verification, the user must select one signed identity and provide exactly two public HTTPS RPC endpoints on different hosts. The reader rejects credentials, query strings, fragments, local/private addresses, oversized responses, malformed JSON-RPC IDs, RPC errors, and timeouts. It sends only `eth_chainId`, `eth_getCode`, and `eth_call`, then runs the full Router/Factory/Pair verifier independently against both readers. Matching results return `verified-design-gate` with `executionEnabled: false`. Official Uniswap repositories expose deployment-address records, but these records can evolve and are treated as evidence candidates until a separately reviewed source signs an exact revision and both current RPC observations agree. Sources: [Uniswap SDK address registry](https://github.com/Uniswap/sdks/blob/main/sdks/sdk-core/src/addresses.ts) and [Uniswap deployment records](https://github.com/Uniswap/contracts/tree/main/deployments) (reviewed 2026-09-01).

`src/swap/external-evm-v2-recovery.ts` defines the post-submission evidence boundary without installing approval or swap submission. A record binds the full validated venue and quote, their recomputed fingerprints, account, chain, pre-submission block, returned transaction hash, nonce, zero value, target, and exact calldata. Approval records accept only `approve(router, amountIn)` and reject unlimited or substituted allowances; swap records require the exact verified Router envelope and may be appended only after a recorded approval is confirmed, unless the future transport used a separately proven pre-existing allowance. Signed raw transactions are deliberately not stored, and every valid record carries a permanent local `resendBlocked` guard.

A manual refresh calls only `eth_chainId`, `eth_blockNumber`, `eth_getTransactionByHash`, `eth_getTransactionReceipt`, and `eth_getTransactionCount(..., \"latest\")` on exactly two independent public HTTPS RPC hosts. Both readers must agree on the exact transaction envelope, receipt, and whether the account nonce has been consumed; their heads may differ by at most twelve blocks, and previously observed reader heads cannot regress. The monotonic state is `submitted → included → confirmed` after two confirmations, or terminal `reverted`. If both the exact transaction and receipt are absent while the nonce is consumed, the state becomes `replacement-unresolved`; later discovery of the exact original may resolve it, but missing evidence never authorizes a retry. EIP-1474 defines the JSON-RPC methods and null receipt result, while Ethereum's transaction and account documentation explains inclusion/finality and per-account nonce uniqueness. Sources: [EIP-1474](https://eips.ethereum.org/EIPS/eip-1474), [Ethereum transactions](https://ethereum.org/developers/docs/transactions/), and [Ethereum accounts](https://ethereum.org/developers/docs/accounts/) (reviewed 2026-09-01).

No reviewed source descriptor, signed public Router/Factory/Pair/path identity, or wallet execution transport is bundled yet. ABI compatibility, a protocol name, an official-looking address list, a frontend label, or a user-entered address cannot enable it. Exact deployed identities and their independent review remain unknown until a separate source and deployment evidence decision is made.

## Solana swap simulation boundary

`src/swap/solana-swap-boundary.ts` establishes a non-executing boundary for one exact Solana swap venue. A descriptor binds the CAIP-2 network, program address, upgradeable-loader owner, program-data account, SHA-256 of the complete program-data bytes, token program, venue revision, and independent evidence URLs. A venue-specific decoder is mandatory; the core does not infer meaning from opaque instruction bytes.

The proposed unsigned transaction must be version 0, contain no address lookup tables or existing signatures, have exactly one signer and exactly one instruction, and target only the described venue program. The decoded instruction must match the authority, source and destination mints and token accounts, token program, exact input, and minimum output. Critical signer/read/write account roles are checked independently. Quote expiry, recent blockhash, last-valid block height, and a bounded remaining lifetime are also bound to the intent. Solana documents the transaction message and account-key model in [Transactions](https://solana.com/docs/core/transactions), while [getAccountInfo](https://solana.com/docs/rpc/http/getaccountinfo) exposes the owner, executable flag, and account data used for program identity (reviewed 2026-09-01).

Two distinct public HTTPS RPC readers must each confirm the chain genesis, program identities, blockhash validity, and a successful `simulateTransaction` result. Source-token debit must equal the exact input; destination credit must equal the quoted output and satisfy minimum output; mints and owners must match; fee and compute use are bounded; and both readers must agree on debit, credit, fee, and compute units. Solana specifies that `simulateTransaction` does not broadcast and may simulate an unsigned transaction when signature verification is disabled; RealDEX keeps recent-blockhash replacement disabled so the exact bound lifetime is tested. Source: [simulateTransaction](https://solana.com/docs/rpc/http/simulatetransaction) (reviewed 2026-09-01).

`src/swap/solana-venue-source.ts` authenticates which reviewer asserted that exact venue identity without turning the assertion into execution permission. A local source descriptor pins one base58 Ed25519 public key, allowed Solana CAIP-2 chains, and HTTPS policy evidence. The signed manifest uses a strict canonical payload with a maximum 30-day validity window and binds its source fingerprint, source ID, revision, all venue descriptors, and evidence. Unknown fields, malformed signatures, source or signer substitution, chain-scope violations, duplicate venue IDs or fingerprints, rollback, and different payloads reusing one revision fail closed. Universe persists only the highest revision and payload hash for that source fingerprint and refuses acceptance if the head is malformed or cannot be written.

The source-bound swap entrypoint re-verifies the Ed25519 signature and revision evidence at the current time, selects the exact signed venue ID, and only then calls the existing transaction decoder, program/ProgramData identity checks, and two-reader simulation boundary. The complete ProgramData account hash binds both loader metadata and deployed bytes; current RPC observations must still match because an upgradeable program can change while its program ID remains constant. Solana documents that the ProgramData account stores deployed executable code and that loader-v3 programs remain upgradeable while an authority is present. Sources: [Solana Programs](https://solana.com/docs/core/programs) and [Deploying Programs](https://solana.com/docs/programs/deploying) (reviewed 2026-09-01).

`src/swap/spl-token-swap-exact-in-decoder.ts` adds a production-shaped decoder for the classic SPL Token Swap `Swap` instruction without enabling a deployment. The official reference encodes tag `1`, `amount_in` u64, and `minimum_amount_out` u64 and declares the pool state/authority, user transfer authority, user and pool token accounts, pool mint/fee account, source/destination mints, three token-program positions, and an optional host-fee account. RealDEX requires exactly 17 instruction bytes, 14 accounts or exactly 15 when a reviewed host-fee account is declared, and exact address plus signer/read/write roles at every position. Sources: [SPL Token Swap instruction source](https://github.com/solana-labs/solana-program-library/blob/master/token-swap/program/src/instruction.rs), [SPL Token Swap documentation](https://github.com/solana-labs/solana-program-library/blob/master/docs/src/token-swap.md) (reviewed 2026-09-01; repository archived 2025-03-11).

The Solana venue and intent now bind an `executionTarget` pool-state address in addition to the program identity. Thus two pools under the same program cannot share authority. Substituted pool vaults, fee accounts, mints, token programs, user accounts, privilege changes, alternate instruction tags, trailing bytes, and zero amounts fail closed. Restricting the three token-program positions to one exact reviewed program is intentional; Token-2022 or mixed-program pools require a separately modeled decoder.

`src/swap/spl-token-swap-quote-boundary.ts` removes the caller's quoted output as a trust root for the supported route. Exactly two distinct public HTTPS RPC hosts each provide genesis, current slot, and one contextual `getMultipleAccounts` snapshot containing the signed pool state and source/destination vaults. The verifier decodes the reference's exact 324-byte versioned swap state and classic 165-byte token accounts, derives the swap authority PDA, binds pool mint, fee account, vaults, mints, token program and direction, validates all four fee fractions, and supports only curve type 0 with canonical zero curve parameters. It then reproduces the reference trade-fee and owner-trade-fee minimum-one rounding plus constant-product invariant/ceiling division. Both readers must agree on reserves, fees, and output; that output and the exact floor implied by the signed 0–500 bps slippage must equal the intent. Sources: SPL Token Swap [state layout](https://github.com/solana-labs/solana-program-library/blob/master/token-swap/program/src/state.rs), [fee calculation](https://github.com/solana-labs/solana-program-library/blob/master/token-swap/program/src/curve/fees.rs), [curve dispatch](https://github.com/solana-labs/solana-program-library/blob/master/token-swap/program/src/curve/base.rs), [constant-product calculation](https://github.com/solana-labs/solana-program-library/blob/master/token-swap/program/src/curve/constant_product.rs), and current SPL Token [account interface](https://github.com/solana-program/token/blob/main/interface/src/state.rs) (reviewed 2026-09-01).

This first quote model deliberately rejects stable, offset, and owner-withdraw curves, Token-2022/extensions, noncanonical or delegated/closing vaults, more than 150 slots of lag or cross-reader divergence, and any disagreement. Distinct hostnames are only a locally checkable anti-single-endpoint rule; they do not prove different operators or upstream nodes. The two reads are not an atomic distributed snapshot, and state may move before simulation. Therefore the source-bound pipeline requires both a matching independently calculated quote and the later matching transaction simulations, while still returning only non-executing evidence.

`src/swap/solana-read-policy.ts` authenticates which RPC pair is allowed to supply those observations. Its source descriptor is independent from the venue publisher and pins an Ed25519 public key, Solana CAIP-2 scope, and evidence. A strict signed policy binds that source fingerprint, one exact chain, two normalized credential-free public HTTPS endpoints on different hosts, the exact quote and simulation boundary IDs, canonical issue/expiry timestamps with at most 30 days of validity, monotonic revision, and evidence. Unknown fields, source/signature/chain/boundary/endpoint substitution, private or same-host URLs, rollback, same-revision equivocation, malformed persisted heads, and expiry fail closed. Verification grants no network, signing, or execution authority by itself.

The source-bound SPL entrypoint no longer accepts abstract readers from its caller. It freshly revalidates the verified read-policy evidence, requires its reviewer key to differ from the route publisher, requires its chain to equal the selected signed route, and constructs both the pool-quote and transaction-simulation readers from only the signed endpoint pair. This prevents a valid route from being combined silently with a same-key self-review, arbitrary RPC text fields, or caller-supplied fake reader identities. It does not establish that two hostnames have separate operators, infrastructure, or upstream nodes; those remain evidence and review questions outside what client code can prove.

`src/swap/solana-spl-route-source.ts` makes that protocol descriptor the signed unit of provenance. The generic Solana venue manifest remains useful for program/pool identity review, but it cannot authenticate an independently supplied protocol decoder. The SPL route manifest therefore binds its source fingerprint, canonical timestamps and maximum 30-day validity, monotonic revision, every program identity field, and the complete ordered pool topology. Its source-bound entrypoint freshly verifies the Ed25519 signature and stored head, selects the exact signed venue ID, derives both `SolanaVenueDescriptor` and the SPL decoder only from that route, verifies the two-reader constant-product pool quote, and only then enters the unsigned-transaction and two-RPC simulation boundary.

Universe exposes this complete path without adding execution. A user pins the route publisher source and the independent read-policy source, imports both signed artifacts, selects one signed route, and imports a strict unsigned v0 intent. RPC fields are read-only and populated only from the accepted policy. Both policy-bound hosts receive the unsigned transaction and account addresses through bounded JSON-RPC POST requests for genesis, pool/vault state, block height, blockhash validity, program accounts, and `simulateTransaction`; `sigVerify` is disabled while recent-blockhash replacement stays disabled. Unknown intent or policy fields, private or same-host endpoints, stale heads, program drift, expired blockhashes, and disagreement fail closed. Success produces only a design-gated evidence report—there is no wallet signature request or `sendTransaction` method. Sources: Solana [`getGenesisHash`](https://solana.com/docs/rpc/http/getgenesishash), [`getMultipleAccounts`](https://solana.com/docs/rpc/http/getmultipleaccounts), [`getBlockHeight`](https://solana.com/docs/rpc/http/getblockheight), and [`simulateTransaction`](https://solana.com/docs/rpc/http/simulatetransaction) (reviewed 2026-09-01).

`src/swap/solana-swap-recovery.ts` defines the family-specific post-submission evidence boundary without installing submission. Creation accepts the exact unsigned intent and prior `VerifiedSolanaSwap`, plus signed transaction bytes and their base58 signature. It requires one 64-byte signature, byte-identical signed/unsigned message bodies, Ed25519 verification against the bound authority, matching transaction and canonical-intent SHA-256 values, and the same pool execution target and last-valid block height. The journal stores bounded diagnostic evidence and a permanent local `resendBlocked` guard; it does not restore quote or signing authority.

A manual future refresh must use two distinct public HTTPS RPC hosts. Both query the exact signature with `searchTransactionHistory: true`, report the same transaction slot and success/failure classification, and agree whether the confirmed block height has passed `lastValidBlockHeight`; differing commitment levels are reduced to the weaker result. Reader height regression, excessive head divergence, disappearing evidence after a stronger stage, chain mismatch, and terminal-stage mutation are rejected. If both readers find no signature after expiry, the stage is `expired-unresolved`: historical pruning or incomplete observation means absence is not proof of non-execution and cannot authorize replay. Solana documents the status cache and history-search option in [getSignatureStatuses](https://solana.com/docs/rpc/http/getsignaturestatuses), block height in [getBlockHeight](https://solana.com/docs/rpc/http/getblockheight), and blockhash expiry handling in [Transaction Confirmation & Expiration](https://solana.com/developers/cookbook/transactions/confirmation) (reviewed 2026-09-01).

Passing this verifier returns only a design-gated evidence object. No public pool descriptor, verified deployed program identity, wallet signature request, transaction submission, quote source, or recovery authority capable of resending is installed. The recovery journal only preserves and refreshes evidence for a transaction submitted by a future separately reviewed transport. A verified simulation or persisted record is not execution permission.

## Cosmos swap transaction boundary

`src/swap/cosmos-swap-boundary.ts` establishes a non-executing boundary for one exact Cosmos SDK swap venue without assuming EVM calldata or Solana account roles. Its descriptor binds the CAIP-2 chain, bech32 prefix, exact protobuf message type, venue execution target, secp256k1 public-key type, venue revision, and independent evidence URLs. A venue-specific protobuf decoder must map the opaque message bytes to the exact authority, recipient, target, denoms, input, and minimum output.

The candidate transaction must be a canonically ordered protobuf `TxRaw` with one message, one signer, one empty simulation-signature placeholder, one fee coin, and `SIGN_MODE_DIRECT`. Memo, extension options, multisig, Amino, fee payer, fee granter, tip, extra messages, unknown fields, and existing signatures are rejected. The raw body and authorization bytes, chain ID, and account number form the hashed `SignDoc`; signer sequence, current public key, exact fee/gas limit, quote expiry, and a bounded timeout height are separately rebound. Cosmos SDK documents that `TxRaw` pins body/auth bytes and `SignDoc` adds chain ID and account number, while sequence in `AuthInfo` provides replay protection. Sources: [Protobuf and Signing](https://docs.cosmos.network/sdk/latest/learn/concepts/encoding), [Transactions, Messages, and Queries](https://docs.cosmos.network/sdk/latest/learn/concepts/transactions) (reviewed 2026-09-01).

Two distinct public HTTPS REST readers must agree on chain ID, current BaseAccount number/sequence/public key, and a successful simulation. The simulator's authority debits must equal exact input plus exact fee, its recipient credit must equal quoted output and satisfy minimum output, and gas wanted/used must fit the signed limit and agree across readers. The Cosmos SDK transaction service defines `POST /cosmos/tx/v1beta1/simulate` over raw transaction bytes, and BaseApp simulation runs without committing state. Sources: [Cosmos SDK transaction service](https://github.com/cosmos/cosmos-sdk/blob/main/proto/cosmos/tx/v1beta1/service.proto), [BaseApp execution modes](https://docs.cosmos.network/sdk/latest/learn/concepts/baseapp) (reviewed 2026-09-01).

The Universe Routes view now exposes this complete verification path without installing execution. After a session-pinned source and signed Osmosis route manifest are accepted, the user selects an exact signed route, imports a strict unsigned intent, and supplies two public HTTPS REST endpoints on different hosts. The implementation freshly re-verifies the source signature and stored revision head before constructing the decoder, then performs bounded node/head/account queries and `POST /cosmos/tx/v1beta1/simulate` against both readers. Unknown intent fields, credentials, localhost/private endpoints, same-host pairs, chain or account drift, expired timeout/quote, and simulation disagreement fail closed. The UI warns that both REST operators receive the account address and unsigned transaction; success remains a design-gated hash/evidence report with no signing or broadcast control.

The bundled REST reader deliberately supports only a direct `/cosmos.auth.v1beta1.BaseAccount`. Chains with wrapped Ethermint, vesting, multisig, textual, or other account/signing models require their own reviewed reader boundary.

`src/swap/osmosis-exact-in-decoder.ts` adds the first production-shaped venue decoder without enabling a pool. It accepts only `/osmosis.gamm.v1beta1.MsgSwapExactAmountIn`: the exact osmo sender, one to four ordered `SwapAmountInRoute` hops, input `Coin`, and final minimum output must match a separately reviewed route descriptor. Each hop binds `pool_id` and `token_out_denom`; duplicate pools, repeated/cyclic denoms, zero or non-canonical integers, reordered/unknown protobuf fields, and split-route messages are rejected. Osmosis defines these fields in its [GAMM transaction protobuf](https://github.com/osmosis-labs/osmosis/blob/main/proto/osmosis/gamm/v1beta1/tx.proto) and [PoolManager route protobuf](https://github.com/osmosis-labs/osmosis/blob/main/proto/osmosis/poolmanager/v1beta1/swap_route.proto). PoolManager documents that each hop's output becomes the next hop's input, the final output must satisfy `tokenOutMinAmount`, and off-chain selected routes may become stale before execution; therefore a decoded route still requires fresh simulation and quote expiry. Source: [Osmosis PoolManager](https://github.com/osmosis-labs/osmosis/blob/main/x/poolmanager/README.md) (reviewed 2026-09-01).

`src/swap/cosmos-venue-source.ts` adds provenance without conflating it with transaction authorization. A local source descriptor pins one compressed secp256k1 publisher key, allowed Cosmos CAIP-2 chains, and HTTPS policy evidence. A strict, domain-separated canonical manifest binds the source ID and fingerprint, canonical issue/expiry timestamps with at most 30 days of validity, monotonic revision, every exact Osmosis route descriptor, and evidence. Signatures must be compact low-S secp256k1; unknown fields, duplicates, source/signer/chain substitution, rollback, and same-revision equivocation fail closed. Universe persists only the highest accepted revision and payload hash for that source fingerprint and refuses acceptance when the head is malformed or cannot be written.

The source-bound entrypoint freshly verifies the signed manifest, selects the exact venue ID, derives both the venue descriptor and Osmosis decoder solely from that signed route, and only then enters the existing canonical `TxRaw` and two-REST simulation boundary. The detached publisher signature is intentionally not a Cosmos account signature over `SignDoc`; it neither requests nor proves wallet authorization and cannot broadcast. Cosmos SDK's ante handler verifies account public keys and transaction signatures, while `TxRaw` pins the body/auth bytes and DIRECT `SignDoc` additionally binds chain ID and account number. Sources: Cosmos SDK [signature verification](https://github.com/cosmos/cosmos-sdk/blob/main/x/auth/ante/sigverify.go) and [`TxRaw` / `SignDoc`](https://github.com/cosmos/cosmos-sdk/blob/main/proto/cosmos/tx/v1beta1/tx.proto), plus [Osmosis PoolManager](https://github.com/osmosis-labs/osmosis/blob/main/x/poolmanager/README.md) (reviewed 2026-09-01).

`src/swap/cosmos-read-policy.ts` closes the remaining reader-provenance gap. Its independently pinned compressed secp256k1 reviewer signs one canonical policy containing the exact Cosmos CAIP-2 chain, two normalized public HTTPS REST endpoints on different hostnames, the installed simulation-boundary ID, at-most-30-day validity, monotonic revision, and evidence. The accepted object is freshly revalidated immediately before reader construction. The source-bound Osmosis entrypoint no longer accepts reader objects, requires the policy chain to equal the signed route chain, requires the reviewer key to differ from the route publisher key, and creates both REST readers only from the signed pair. Universe persists only the policy revision/payload-hash head, renders the endpoints read-only, and invalidates successful evidence when source or policy changes. This proves endpoint authorization by the pinned reviewer, not operator independence, endpoint honesty, liquidity, quote quality, wallet authorization, or permission to broadcast.

`src/swap/cosmos-swap-recovery.ts` defines the family-specific post-submission evidence boundary without installing broadcast. Creation accepts the exact unsigned intent, its prior `VerifiedCosmosSwap`, the signed `TxRaw`, and a broadcast-returned hash. The signed body/auth bytes must be byte-identical to the simulated transaction. RealDEX derives the bech32 authority as RIPEMD-160(SHA-256(compressed secp256k1 public key)), verifies one 64-byte low-S signature over the DIRECT `SignDoc`, and recomputes the unsigned transaction, signed transaction, sign-document, and canonical-intent hashes. The journal deliberately stores hashes and bounded evidence rather than signed transaction bytes, so restoring it cannot provide rebroadcast material or quote/signing authority.

A manual future refresh must use two distinct public HTTPS Cosmos REST hosts. Both bind the node-reported chain ID and committed head, query the exact SHA-256 transaction hash through `GET /cosmos/tx/v1beta1/txs/{hash}`, and must agree on transaction height, result code, codespace, and gas. A committed block is the chain result: code zero is success and nonzero is committed failure. Reader head regression, excessive divergence, a transaction above a reader head, timeout-violating success, split presence, response disagreement, and terminal receipt changes are rejected. Timeout height is inclusive: successful inclusion at that exact height is valid; only a later successful inclusion conflicts. A committed nonzero timeout failure can occur later. If neither indexed history contains the hash after both heads exceed the signed timeout height, the record becomes `expired-unresolved`, because missing index/history is not proof of non-execution and cannot authorize replay. Sources: [Cosmos SDK transaction service](https://github.com/cosmos/cosmos-sdk/blob/main/proto/cosmos/tx/v1beta1/service.proto), [SDK timeout-height check](https://github.com/cosmos/cosmos-sdk/blob/v0.50.14/x/auth/ante/basic.go), and [transaction lifecycle and commit](https://docs.cosmos.network/sdk/v0.50/learn/beginner/tx-lifecycle) (timeout and query boundaries reviewed 2026-09-02).

`createCosmosSignedSwapRecoveryRecord` provides a separate `signed-not-submitted` entrypoint with the same cryptographic transaction binding. The reserved DIRECT signing transport returns this bounded, byte-free recovery snapshot after genuine signature verification and persistence of the blocking signing receipt. It rechecks account, source, provider, expiry and persisted slot before returning. A hash or missing history never promotes this initial state to `submitted`: only matching committed observations can establish a chain result; absent history retains the initial state or becomes unresolved after timeout. The snapshot is page-local and is not automatically saved by the signing UI. No network lookup is triggered by signature verification.

Recovery refresh snapshots records, reader IDs/methods and response primitives before awaiting; callers cannot switch a pending query to another hash or overwrite its returned receipt by mutation. Once committed, height, code, codespace and gas fields cannot change even when the success/failure label is unchanged. Restoration checks the two observations against each other, reader heads, timeout and stage. Structural validation is not authentication against coordinated tampering, and two agreeing REST services are not a light-client proof. GET requests omit credentials/referrers, disallow redirects, limit response size and enforce an end-to-end deadline even if an injected fetch ignores abort. Errors are normalized without exposing response bodies or provider diagnostics.

Public venue rollout, policy-bound recovery UI, durable recovery integration with concurrency/retention guarantees, reservation reconciliation/release, real-extension/hardware compatibility and broadcast remain unfinished. The signature-only UI described above is installed; neither it nor a recovery record grants permission to submit or retry.

### Policy-bound Cosmos recovery reads

The Cosmos signed read-policy payload can now explicitly include `recoveryBoundaryId: "cosmos-swap-recovery-v1"`. This optional field is part of the signature, not a local toggle. Legacy simulation-only payloads retain their canonical encoding and continue to verify, but cannot authorize recovery reads. Adding, stripping or changing the field invalidates its signature; unsupported values reject. An already accepted revision cannot be changed in place to add this purpose: the existing monotonic-head and same-revision conflict checks still apply.

`src/swap/cosmos-policy-bound-recovery.ts` joins genuine page-local signed evidence, its exact recovery record, and a freshly verified recovery-enabled policy. It matches the chain, transaction and intent hashes, authority, recipient, amounts, fee, sequence, signature metadata and original observation time. It requires the same pinned policy-source fingerprint as the original signed evidence, but allows a current policy renewal by that same reviewer. Old quote/account/source expiry does not erase a historical signature or prevent read-only diagnosis; the new read policy itself must remain valid.

The service reads the current accepted revision/payload-hash head before network activity, at each request/response boundary and before returning. A missing, malformed, unavailable or changed head fails closed. It constructs the two REST readers only from the signed endpoint pair, uses GET-only status lookups, snapshots caller-owned selectors, forwards cancellation through body consumption, and discards late results. The returned receipt includes the exact policy fingerprint/hash/revision and check time; it keeps execution and broadcast disabled and resend blocked. Policy/head changes never authorize a replacement lookup automatically. This entrypoint neither uses wallet methods nor writes/deletes storage.

This service is not yet wired to a recovery button or a durable recovery journal. The `readHead` dependency must be supplied by the application's current accepted-head store; a caller-provided head or clock is not independent evidence. Structural recovery-record validation is not storage authentication, and agreement between approved REST endpoints is not a consensus/light-client proof. Imported JSON cannot recreate the genuine signed-evidence capability; reload recovery still requires a separately reviewed reconstruction path. Synthetic tests cover opt-in tampering, genuine-evidence binding, source/chain changes, current-head checks, expiry, cancellation and reviewer renewal without real wallet or chain access.

## Public-network release boundary

The first “real DEX” lane is not another executable trading route.
