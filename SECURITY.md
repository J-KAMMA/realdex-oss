# Security policy

RealDEX（リアルデックス） v0.1 is an unaudited experiment. It is not certified safe for production or real assets.

A configured REST endpoint's IBC acknowledgement value and proof height are observations, not verified proof. Reported success and error both remain non-terminal and keep retry blocked until the acknowledgement membership proof is independently verified against an accepted trusted header. Legacy locally stored IBC terminal claims derived from REST acknowledgement evidence are rejected.

Bridge status and IBC channel readers accept only bounded, credential-free HTTPS GET responses: eight seconds maximum, one megabyte maximum, strict JSON, no referrer, and no cache reuse. Only explicitly expected bodyless statuses are accepted. Timeout, oversize, malformed JSON, transport failure, or an unexpected status fails closed, leaves previously persisted evidence authoritative, and never grants success or retry authority.

New CCTP finality cursors bind the exact source burn token, base-unit amount, source message sender, and destination mint recipient from the confirmed route request. Refresh parses the fixed CCTP V2 raw-message fields locally and compares all four values plus both domains; it does not treat Circle's decoded JSON projection as transfer identity. Malformed, ambiguous, or different valid messages add no evidence. Historical unbound cursors remain visible for reconciliation but cannot issue another status request or acquire new finality evidence.

When Base Sepolia or Arbitrum Sepolia is the CCTP source, Circle's message is not accepted as source-chain evidence by itself. Two distinct public RPC hosts must agree on chain ID, head proximity, successful transaction receipt, block number/hash, complete normalized log list, and exactly one canonical `MessageSent(bytes)` event from the reviewed MessageTransmitterV2 address. Its ABI payload must equal Circle's raw message byte-for-byte and have at least two source confirmations. Any absent, one-reader-only, reverted, divergent, malformed, duplicate, or under-confirmed result preserves `source-submitted`. Later EVM CCTP stages require the persisted source transaction and source-log evidence pair, preventing local stage-only mutation.

For an EVM CCTP destination, Circle's `forwardTxHash` grants no confirmation authority. Two distinct destination RPC hosts must agree on the full successful receipt, block identity and logs with at least two confirmations. The reviewed MessageTransmitterV2 must emit exactly one canonical `MessageReceived` matching the raw nonce, source domain, header sender, executed finality and complete message body. The reviewed TokenMessengerV2 must also emit exactly one V2 `MintAndWithdraw` matching the EVM recipient, reviewed destination USDC, burn amount minus `feeExecuted`, and the same executed fee. Missing, reverted, divergent, malformed, duplicate or under-confirmed evidence remains destination submitted. A persisted EVM `destination-confirmed` record without its exact destination transaction, message and mint evidence is rejected, including older optimistic claims. Solana source and destination program/account verification remain release gates.

The Base Sepolia CCTP execution lane is additionally paused as of 2026-09-02. Two independently hosted pinned RPC readers initially both returned `0x` for `eth_getCode` at Circle's documented Base Sepolia USDC address; a later recheck found the proxy code restored on both. Because an unexplained disappearance and restoration cannot itself establish a safe release, all four Base-dependent CCTP directions remain disabled before any account request or quote call. A user-triggered read-only verifier now requires both hosts to agree within 12 blocks on exact proxy code, the implementation address held in Circle's documented Zeppelinos slot, exact implementation code, and strict `name`, `symbol`, and `decimals` ABI results. Missing code, malformed metadata, wrong chain, excessive head divergence, or any identity disagreement fails closed. Even a matching result is observation evidence only and is structurally incapable of enabling execution. Release requires independent source/bytecode review and an explicit gate change; read-only historical finality refresh remains available.

The signed CCTP asset release-review boundary cannot convert that observation into execution authority. It requires a separately pinned reviewer-source fingerprint and EIP-191 signature over the exact observation fingerprint, reader identities, minimum block, proxy and implementation hashes, fixed Circle repository URL, commit, compiler, optimizer settings, source-file hashes, verification-artifact hash, recommendation, evidence, revision, issue time, and expiry. Observations expire after 24 hours; manifests last at most seven days and cannot predate their observation. Source substitution, signer substitution, evidence mutation, rollback, same-revision conflict, and mutated authority flags fail closed. A verified result still fixes execution, signing, and submission false and explicit user release approval true. No production reviewer trust root or signed production manifest is configured.

Bridge recovery reservations are not created during wallet connection. They are prepared only after active-account revalidation, duplicate detection, and exact durable execution-guard persistence, but before the adapter is invoked. Pre-adapter connection, network, account, duplicate, or guard failures cannot create a false ambiguous-submission warning. If reservation preparation fails, adapter execution does not begin and the new guard is removed only through verified storage deletion; an unverifiable deletion remains fail-closed. Quote ID and execution ID reuse with a different counterpart is rejected before any reservation write.

Before any public-chain deployment:

1. commission an independent Solidity audit and publish the exact source/compiler/settings correspondence;
2. add invariant, fuzz, adversarial-token, and fork tests;
3. verify bytecode and constructor arguments on the target explorer;
4. test wallet, RPC outage, reorg, replacement, stale quote, allowance, and recovery paths;
5. review token compatibility and reject rebasing, transfer-fee, callback, blacklist, or otherwise non-standard assets unless explicitly supported;
6. conduct jurisdiction-specific legal review of the implementation and distribution model;
7. use a new deployment if any defect is found—the contracts have no admin or upgrade path.

Signed token sources are metadata authentication, not an execution allowlist. Before trusting a production source, independently verify its public signer, rotation/revocation policy, allowed-chain scope, publication evidence, and incident process. A valid signature, matching symbol, or matching ERC-20 metadata does not establish safe token behavior, liquidity, bridge equivalence, or permission to trade.

Automatic EVM venue discovery accepts only the compiled `LocalSwapFactory` runtime hash pinned by this build, then verifies the returned pool's bytecode, immutable factory origin, and exact token pair. A compatible ABI, symbol, address label, or user-entered pool is not enough. Any Solidity compiler or factory source change must deliberately update the pinned identity and pass the artifact-hash test after review.

External V2-style AMMs have a separate boundary and never inherit trust from RealDEX v1. The verifier requires exact Router, Factory, and Pair runtime hashes; Router-to-Factory and Factory-to-Pair identity; Pair origin and ordered tokens; and a simple path of at most three hops. It independently recomputes every output from reserves with the exact 997/1000 formula, requires Router `getAmountsOut` agreement, decodes the generated `swapExactTokensForTokens` calldata, and rechecks identity before any future execution. This does not support fee-on-transfer tokens, alternate fee constants, proxy upgrades, arbitrary V2 forks, or a public venue merely because its ABI is compatible. No external venue is enabled in this release.

External V2 recovery remains non-executing and accepts only an exact-size ERC-20 approval to the verified Router or the exact verified swap envelope. The account, chain, target, zero value, calldata, nonce, returned hash, pre-submission block, venue, and quote are bound into a strict revisioned record; signed raw transaction bytes are never persisted. Exactly two independent public HTTPS RPC readers must agree on transaction and receipt evidence, whether the account nonce has been consumed, and sufficiently close chain heads. Missing transaction and receipt evidence after nonce consumption becomes `replacement-unresolved`: it is not evidence that the swap did not execute and never clears the resend block.

External V2 venue provenance is separately fail-closed. A signed manifest is accepted only against the exact fingerprint of a session-pinned source descriptor, its EIP-191 signer, EIP-155 scope, canonical timestamps, at-most-30-day validity, monotonic revision head, and strict JSON schema. Unknown fields cannot smuggle execution flags or credentials into the record. A separate read-policy source pins an EIP-191 reviewer whose address must differ from the venue publisher and whose v2 signed policy binds the exact chain, normalized two-host RPC pair, venue-identity and quote-boundary versions, expiry, revision head, and evidence. The source-bound wrapper accepts neither caller-created readers nor editable endpoint fields: it freshly verifies both signed artifacts, selects the exact manifest venue, constructs readers only from the signed policy, and then rechecks every Router, Factory, Pair, path token, runtime hash, fee model, and contract relationship using only `eth_chainId`, `eth_getCode`, and `eth_call`. Quote requests require a strict canonical intent binding the exact venue, EIP-155 chain, uint256 base-unit amount, non-zero recipient, 0–500 bps slippage, canonical issue time, and a lifetime no longer than five minutes. The generated transaction deadline cannot outlive that intent. Each policy-selected reader independently reproduces the constant-product path from live reserves and matches its Router response, then exact cross-reader agreement is required on amounts, minimum output, deadline, quote ID, and calldata. After the quorum returns, the manifest, policy, intent expiry, and final deadline are revalidated at completion time; an intent expiring during RPC collection is rejected. One valid but different snapshot stops as RPC divergence; it is never silently averaged or ranked. The non-executing preflight rejects malformed or authority-mutated accepted reports, freshly repeats both policy readers, and succeeds only when the exact intent fingerprint, venue/source/policy bindings, amounts, minimum, recipient, deadline, quote ID, calldata, and reader observations remain unchanged. A changed snapshot discards the old quote and requires renewed review. Universe removes green evidence at the earliest quote, venue-manifest, or read-policy expiry and invalidates it on any upstream change. Malformed or unwritable stored heads fail closed. A valid signature proves publisher or reviewer attribution, not deployment safety; matching bytecode and quotes prove neither token behavior, future liquidity, economic safety, operator independence, nor permission to trade. No production source, public venue, read policy, reviewed operator pair, signing, submission, or execution authority is bundled in this release.

Solana venue provenance is independently fail-closed and does not inherit trust from token metadata or a typed pool address. A strict source descriptor pins one Ed25519 public key, allowed Solana CAIP-2 chains, and review evidence. Its signed manifest binds the source fingerprint, canonical timestamps, at-most-30-day validity, monotonic revision head, exact program, loader owner, complete ProgramData SHA-256, token program, pool execution target, and evidence. Unknown fields, altered signatures, source or chain substitution, duplicate venues, rollback, and same-revision equivocation are rejected. The source-bound swap wrapper freshly repeats this verification before the two-RPC program and simulation checks. A publisher signature identifies the publisher's assertion; it does not prove current bytecode, upgrade safety, pool state, token behavior, liquidity, quote quality, wallet authorization, or permission to submit. No Solana publisher or public venue is bundled.

The SPL Token Swap compatibility decoder does not trust a program name or ABI. It binds one exact program-data identity and pool-state execution target, all fourteen required account positions, an explicitly declared optional host-fee account, roles, exact-input amount, and minimum output. Its quote gate additionally derives the pool authority PDA and reads the exact swap state plus both vaults from two hosts. Both must agree on classic token-account ownership and balances, constant-product curve, all fee fractions, topology, independently calculated output, and the exact minimum implied by 0–500 bps slippage. Unsupported curves, Token-2022 extensions, delegated/closing vaults, stale snapshots, malformed COptions, and substituted state fail closed. The upstream reference repository is archived, so its source and historical deployment table are protocol-format evidence only—not proof that any current deployment, pool, liquidity, or token is safe or enabled.

The protocol-specific Solana route source signs that entire decoder descriptor: program and ProgramData identity, pool state and authority, vaults, pool mint, fee and optional host-fee accounts, source/destination mints, token program, chain, revision, expiry, and evidence. A separate Solana read-policy source pins an Ed25519 reviewer whose key must differ from the route publisher and whose signed policy binds the exact chain, normalized two-host RPC pair, quote and simulation boundary versions, expiry, revision head, and evidence. The source-bound wrapper accepts neither caller-created readers nor editable endpoint fields: it freshly verifies both signed artifacts, derives its venue/decoder and both reader quorums, then performs pool-state quote verification and simulation. Universe discloses that both policy-selected RPC operators receive the unsigned transaction and account addresses; it uses bounded JSON-RPC POST requests and exposes no signing or `sendTransaction` path. A signed pair prevents silent endpoint substitution but does not prove operator/upstream independence, snapshots are not atomic, and agreeing checks still do not prove token safety, durable liquidity, wallet authorization, or permission to submit.

Solana recovery verifies a submitted Ed25519 signature over the exact previously simulated message before persisting it. Two independent RPC histories must agree on the signature slot and success/failure; commitment is deliberately reduced to the weaker observation. An absent signature after blockhash expiry remains `expired-unresolved` because RPC history may be incomplete. It never clears the duplicate guard or authorizes resubmission.

Cosmos recovery verifies that the signed `TxRaw` preserves the exact simulated body and authorization bytes, derives the bound bech32 authority from the secp256k1 public key, and accepts only one valid canonical 64-byte low-S signature over the DIRECT `SignDoc`. It recomputes the signed transaction hash and never stores signed bytes for rebroadcast. Two independent REST histories must agree on the exact committed height, code, codespace, and gas. An absent indexed transaction after timeout remains `expired-unresolved`; it is not evidence that execution did not occur and never authorizes rebroadcast.

Cosmos/Osmosis venue provenance is a separate fail-closed publisher assertion. A strict source pins one compressed secp256k1 public key, Cosmos CAIP-2 scope, and evidence; its domain-separated detached signature binds a maximum-30-day canonical manifest, monotonic revision head, exact ordered pool IDs and hop denoms, and every route/evidence field. High-S signatures, unknown fields, expiry, rollback, same-revision equivocation, duplicate routes, source/signer/chain substitution, and malformed or unwritable local heads are rejected. A separate read-policy source pins a low-S secp256k1 reviewer whose key must differ from the route publisher and whose signed policy binds the exact chain, normalized two-host REST pair, simulation-boundary version, expiry, revision head, and evidence. The source-bound wrapper accepts neither caller-created readers nor editable endpoint fields: it freshly verifies both signed artifacts, creates the REST quorum only from the accepted policy, and then runs the exact `TxRaw` checks. This publisher signature is not a Cosmos account signature, `SignDoc` authorization, wallet capability, proof of current pool state/liquidity/price, or broadcast permission. Distinct hostnames do not prove operator or upstream independence. No production Cosmos publisher, public Osmosis route, read policy, or reviewed operator pair is bundled.

The Universe Cosmos simulation workflow accepts only a strict unsigned intent with an exact field set. It requires two public HTTPS REST hosts on different hostnames, bounds response size and timeout, omits credentials/referrer/cache, and calls only node/head/account GET endpoints plus the non-committing transaction simulation endpoint. It never exposes a broadcast call. The unsigned transaction and account address are nevertheless disclosed to both selected REST operators, so endpoint privacy and trust remain explicit user-visible boundaries. Endpoint agreement is not proof of independence or honesty, and no production endpoint pair is bundled.

Atomic multi-hop execution additionally accepts only the compiled `LocalSwapRouter` runtime hash pinned by this build. Every ordered pool and token pair is rechecked before quoting and again immediately before value movement. Paths are limited to four hops and reject repeated pools or tokens. The router has no administrator and successful execution retains no path funds, but it is unaudited; do not deploy it for real assets without independent review, invariant/fuzz testing, and adversarial-token testing.

EIP-6963 wallet metadata is self-asserted. RealDEX validates the announcement shape, requires UUIDv4 and data-URI icons, does not use reverse-DNS for feature detection, and quarantines duplicate UUIDs with inconsistent provider objects or metadata. It does not render announced icons, avoiding SVG-script ambiguity. Provider selection is not connection or authorization; changing the selected provider invalidates the connected account and every active quote.

Wallet execution grants are short-lived and exact-chain. Local provider bindings state only what the installed adapter observes and requires; they are not represented as wallet-negotiated permissions. CAIP-25 responses are parsed as untrusted input and must grant the exact CAIP-10 account, method, and notifications used by the route. A valid grant does not install or authenticate its transport, prove wallet safety, or authorize any route whose reviewed adapter is missing.



The Bitcoin PSBT inspector accepts only canonical base64 BIP-174 version 0 documents containing one legacy-serialized unsigned transaction. Every input must be an exact native P2WPKH or P2TR witness UTXO bound to the declared outpoint, amount, address, and sequence. Every output is ordered and bound to an exact network-validated address and amount; input minus output must equal the declared fee, and transaction version, locktime, and a maximum 15-minute intent lifetime are exact. Duplicate/non-minimal keys, unknown fields, PSBT v2, non-witness UTXOs, P2SH/P2WSH inputs, partial/final signatures, unsafe sighashes, output metadata, count changes, and trailing data fail closed. A valid report proves only that the file matches its self-contained intent. It does not prove UTXO existence or ownership, fee reasonableness, price, liquidity, counterparty behavior, or swap atomicity, and it cannot sign, finalize, broadcast, or authorize a wallet request.

The optional Bitcoin UTXO verifier re-inspects the same unexpired PSBT intent, then asks exactly two distinct public HTTPS Esplora hosts for the genesis block hash, tip height, transaction output, confirmation status, and outspend state using GET only. Credentials, query strings, fragments, local/private hosts, duplicate hosts, oversized responses, timeouts, wrong-chain genesis prefixes, altered values/scripts, spent or unconfirmed outputs, insufficient confirmations, excessive tip divergence, and reader disagreement fail closed. Changing the PSBT or either endpoint invalidates a late UI result. Esplora operators can observe queried outpoints and two operators may share infrastructure or bad data, so quorum is corroboration rather than privacy, ownership, or consensus proof. Success never enables signing, finalization, submission, broadcast, or swap execution.

The Bitcoin fee gate derives a conservative signed virtual-size interval without producing a signature: the stripped unsigned transaction is weighted at four units per byte, SegWit marker/flag and supported P2WPKH or P2TR key-path witness bounds are added, and weight is rounded up to vbytes. The exact declared fee therefore becomes a bounded milli-sat/vB interval. Only after the same PSBT and UTXO report are rebound does the gate query both Esplora `/fee-estimates` responses for a six-block target. Missing or over-precise estimates, unsupported targets, more than 50% reader divergence, rates below both the absolute 1 sat/vB floor and 0.5× the higher recommendation, or above the absolute 1000 sat/vB ceiling or 5× the lower recommendation fail closed. Estimates are third-party forecasts and do not guarantee confirmation, inclusion, fee optimality, or honest operation; the default policy is an inspection guard and is not silently treated as a production policy.

The Wallets screen does not let a manually typed Esplora URL plus built-in defaults initiate Bitcoin reads. The user must first pin a local source descriptor whose fingerprint fixes an EIP-191 publisher, BIP122 chain scope, and evidence. A signed policy then fixes that source fingerprint, exact chain, two normalized independent public HTTPS hosts, all UTXO and fee thresholds, evidence, a maximum 30-day lifetime, and revision. The signature is policy provenance only; it is not a Bitcoin key, wallet connection, transaction signature, or authorization to move value. A per-source local revision/payload-hash head blocks rollback and same-revision equivocation. The full signature, endpoints, PSBT, and publisher key are not persisted. The policy is revalidated immediately before every network read, and chain mismatch, expiry, or state substitution stops before fetch. No production publisher or policy is bundled.

The wallet-returned signed-PSBT verifier runs only after the exact unexpired intent, UTXO quorum, fee gate, and signed read policy are rebound. It requires the unsigned transaction, global map, output maps, witness UTXOs, derivation data, and sighash declarations to remain unchanged. P2WPKH signatures must be strict low-S DER ECDSA with `SIGHASH_ALL` and a compressed public key matching the witness program. P2TR is key-path only and accepts BIP-340 Schnorr with canonical `SIGHASH_DEFAULT` or `SIGHASH_ALL`. Final scripts, Taproot script paths, extra metadata, unsafe hash modes, missing signatures, altered keys, stale evidence, and envelopes over five minutes fail closed. Verification does not prove the wallet UI was honest or authorize extraction, finalization, broadcast, retry, or a swap.

The finalized-PSBT verifier does not finalize a PSBT. It accepts a separate, maximum-five-minute external result only after freshly repeating signed-PSBT verification and matching its exact fingerprint. Each native witness input must retain the exact witness UTXO, remove signing metadata, omit `finalScriptSig`, and contain one canonical `finalScriptWitness` whose items byte-match the already verified signature and public key. It computes txid from traditional serialization and wtxid from witness serialization, plus exact BIP-141 weight/vsize, entirely in memory. Raw transaction bytes are not returned or persisted, and no extractor or broadcaster is exposed. A successful report is still not mempool acceptance, relay, mining, confirmation, replacement, swap, or retry authority.

Do not include private keys, seed phrases, API keys, wallet exports, or live credentials in bug reports.

Bridge finality records and pre-execution reservations in browser storage are untrusted recovery hints, not proof. RealDEX accepts them only when their schema, route fingerprint, request fingerprint, quote, execution, provider, protocol cursor, evidence limits, and timestamps validate against the currently selected reviewed route. Current records use a cryptographic route/execution/quote operation key, retain up to 16 records plus reservations per route, and reject an execution or quote reused with a different counterpart. Before entering the adapter, a quote-bound reservation must survive byte-identical storage readback. A validated Circle event must be exactly CCTP v2 `burn`, successful, contain a valid source transaction identifier, and carry no unsafe explorer URL or error text before it can synchronously replace that reservation; approval, mint, pending, malformed, or HTTP evidence is ignored. The final provider receipt is reconciled onto this durable progress record without resetting creation time or revision. Updates must advance exactly one revision, preserve identity, cursor, creation time, and every prior evidence item, follow a legal state transition, and survive byte-identical storage readback. A route-fingerprint-derived exclusive Web Lock covers reservation through wallet execution and finality persistence, so two tabs cannot both consume the last recovery slot. The same lock makes refresh reload the durable latest record before checking and keeps its network observation and save in one critical section. Lock contention or service failure is fail-closed; localStorage is not used as a non-atomic fallback. A reservation left without a source identity remains visible as an ambiguous attempt and forbids retry; it is removed only after the common engine returns a validated terminal no-value-transfer failure proof. A later transfer therefore cannot overwrite an older unresolved transfer. Historical v1 and legacy-fingerprint records remain selectable for read-only tracking but cannot accept an update. A failed initial save is disclosed without pretending recovery evidence was retained, and a failed refresh save preserves the prior state. Status refresh is also operation-ID guarded so a late response cannot replace the selected record or a newly selected route. A CCTP Bridge Kit `success` result remains `awaiting-proof`; forwarding transaction discovery is shown as destination submitted, never independently finalized. An IBC acknowledgement returned by a configured REST endpoint can establish the UI's observed destination result, but this release does not independently verify its Merkle proof against a locally trusted header. Missing status, an expired packet timeout, an unavailable provider, provider-reported completion, or a full/invalid local journal is never sufficient evidence to retry, refund, or submit a second source transfer.

The newer EVM destination quorum above supersedes the earlier blanket statement that forwarding discovery can never be independently finalized: it remains destination submitted for Solana destinations and for incomplete EVM evidence, but reaches destination confirmed only through the exact two-RPC message-and-mint proof. Bridge Kit success alone remains source submitted, not awaiting proof.

Route descriptors, quote requests, wallet execution grants, legacy bridge descriptors, execution guards, and new EVM recovery records use a canonical typed encoding with a distinct RealDEX domain and Keccak-256. This prevents a 32-bit non-cryptographic fingerprint from serving as financial authority and binds fields that earlier legacy bridge identifiers omitted. Exact historical FNV route/finality and EVM recovery records remain parseable only for status tracking. They cannot be extended with a new transaction or satisfy a current quote, execution, or recovery identity.

The browser duplicate-execution guard is a permanent fail-closed lock for one cryptographically random human execution intent on one exact route. The intent ID is part of every route-request fingerprint but is independent from quote expiry, quote ID, and wallet-grant expiry, so refreshing those values cannot create retry authority. Swap and Bridge keep it across re-quoting and rotate it when transaction-defining input, direction, route, or wallet authority changes. Before account connection, an origin-wide exclusive Web Lock covers the complete check/write/adapter critical section; a concurrent tab receives no lock and cannot reach its wallet. Web Locks service failure or absence stops rather than falling back to the non-atomic localStorage check. Inside that lock, the v3 guard is written and read back before the execution adapter is called. Storage denial, quota failure, or readback mismatch stops before submission; malformed storage and every legacy route guard remain blocking instead of being deleted. There is no elapsed-time inference that a pending or unknown operation is safe to resend. A `failed` label alone never releases the lock: the receipt must carry a validated proof that no value-transfer transaction was submitted, that the exact EVM transfer reverted with a status-zero receipt, or that the exact Cosmos source transaction returned a non-zero code. Provider errors, transaction identifiers without terminal evidence, changed replacements, confirmed/pending/unknown results, exceptions, and timeouts retain it. Adapter progress is validated before reaching the UI and may only report `pending`; false terminal progress cannot create a premature success or retry surface. Clearing browser site data can still destroy this local evidence, so the route-specific transaction/finality recovery record remains the authoritative status aid and users must not infer non-execution from missing local data.

Public deployment is a separate R3 action. The deployment verifier (Base, Arbitrum One and their Sepolia testnets) is read-only: its plan binds the exact source bundle, compiler settings, and pinned Factory/Router runtime hashes, while its post-deployment verifier requires matching successful receipts and bytecode from at least two independently identified RPC readers. Browser readers accept only public HTTPS endpoints on distinct hosts, omit credentials/referrer, do not persist URLs, time out instead of inferring a result, and call only four read methods. URL credentials, query parameters, localhost, and private-network addresses are rejected; do not paste provider API secrets. The manifest schema is strict and accepts no private-key, mnemonic, or unknown fields. Structural evidence acceptance and on-chain verification are not deployment authorization, and testnet verification never enables mainnet or initial liquidity. See `docs/REAL_DEX_RELEASE_GATE.md`.
